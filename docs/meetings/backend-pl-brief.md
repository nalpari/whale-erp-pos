## 2. 처음 1분에 말할 것

1. 매장 PC에 설치하는 주문접수 프로그램을 만든다. 결제가 끝난 주문을 받아 접수하고 주문서를 출력한다.
2. 주문 누락 0건이 목표다. 그래서 전달 방식과 별개로 수신 확인, 주기적 조회, 중복 제거가 필요하다.
3. 오늘 정하고 싶은 것은 전달 방식, 담당, 조회 API 형태, 일정이다.

## 4. 내 의견으로 말할 것

- **파일럿은 짧은 폴링(3초 간격)으로 시작하고 싶다.**
  - 백엔드가 새로 만들 것이 조회 API 하나다.
  - 이 요청 하나로 새 주문 수신, 고객 취소 수신, "매장 프로그램이 켜져 있음" 신호를 함께 처리한다.
  - 서버가 여러 대여도 문제가 없다. 어느 서버가 받아도 데이터베이스를 보고 답한다.
  - 대가는 최대 3초 지연이다. 전달 지연 목표를 "5초 이내"로 잡고 싶다.
- **수신 부분만 갈아 끼울 수 있게 만든다.** 매장이 늘면 다른 방식으로 바꿀 수 있다.
- **확장 단계 후보는 두 가지로 본다. 1순위는 SSE다.**
  - 1순위, SSE + 서버끼리 알려 주는 장치(Redis 등): 기존 HTTP 서버와 443 포트를 그대로 쓴다. 서버끼리 알려 주는 장치는 백엔드가 만든다. 배달의민족이 최종적으로 고른 방식이다(아래 "배달의민족 사례").
  - 2순위, MQTT + 느린 폴링(30~60초): 관리형 브로커가 연결과 라우팅을 맡는다. 새 서비스 계약과 매장별 인증 정보 관리가 필요하다. 배달의민족은 일부 매장 방화벽이 MQTT 포트를 막아 폴링을 뗄 수 없었고, 결국 SSE로 옮겼다.
  - 어느 쪽이든 폴링은 간격을 늘려 누락 방지용으로 남긴다.
- **매장에서 백엔드로 보내는 요청(접수, 거절, 취소 등)은 전부 REST API로 보낸다.**
- **취소·변경 정책 제안**: 고객 취소는 매장 접수 전까지만 받는다. 겹치면 백엔드가 먼저 도착한 쪽을 인정한다. 매장은 접수 성공 응답을 받은 뒤에만 주문서를 출력한다. 결제 후 메뉴 변경은 허용하지 않는다.

### 배달의민족 사례 (회의에서 근거로 쓸 수 있는 것)

상세와 인용은 `docs/research/store-order-delivery-industry-practices.md`에 있다. 매장 단말로의 전달 방식을 회사가 직접 밝힌 곳은 조사한 서비스 중 배달의민족뿐이었다. 스타벅스, 메가커피, 매머드커피 등은 확인하지 못했다.

| 사실 | 이 회의에서의 의미 | 출처 |
|---|---|---|
| 주문접수 프로그램의 전달 방식을 짧은 폴링 → MQTT → SSE 순서로 바꿨다 | "파일럿은 폴링, 매장이 늘면 SSE"는 실제로 있었던 경로다 | [우아한형제들 기술블로그 2017-08-11](https://techblog.woowahan.com/2540/), [2025-10-24](https://techblog.woowahan.com/23199/) |
| 폴링을 버린 이유는 매장 증가에 따른 서버 부하와 비용이다 | 폴링은 규모가 커지면 바꿔야 한다. 파일럿 규모에서는 해당하지 않는다 | 같은 글 |
| MQTT는 일부 매장 네트워크의 방화벽이 1883/8883 포트를 막아, 폴링을 함께 돌려야 했다 | MQTT를 확장 단계 2순위로 둔 이유 | 2025-10-24 글 |
| WebSocket이 아니라 SSE를 고른 이유는 서버 → 매장 한 방향이면 충분했기 때문이다 | 매장 → 서버를 REST로 두는 우리 구조와 같다 | 같은 글 |
| SSE에 더해 중요한 이벤트마다 수신 확인을 받고, 재연결 시 `Last-Event-ID`로 놓친 메시지를 다시 보낸다 | 수신 확인과 재전송은 SSE를 써도 따로 필요하다 | 같은 글 |
| 서버가 여러 대일 때 모든 SSE 서버가 메시지를 받는 방식(메시지 브로커, Kafka)을 골랐다 | 부록 "서버 구성 그림" 2번과 같은 구조다 | 같은 글 |
| 수신부를 갈아 끼울 수 있게 만들어, MQTT → SSE 전환 때 그 부분만 바꿨다 | 협의 문서 5장의 "수신 모듈만 교체"가 실제로 쓰인 사례다 | [2025-12-16 글](https://techblog.woowahan.com/24337/) |

- 위 표의 MQTT 포트 차단, SSE 선택 이유, 수신 확인, 브로커 선택은 2026-11-16에 블로그 원문을 직접 열어 확인했다.
- 배달의민족은 매장 수만 곳 규모다. 방식을 바꾼 이유가 모두 규모에서 나왔으므로, 매장 1곳 파일럿에 SSE와 Kafka를 그대로 가져올 근거는 아니다.

**운영 규칙 참고 (질문 4와 관련)**

| 서비스 | 접수하지 않은 주문 | 출처 확인 수준 |
|---|---|---|
| 배달의민족 | 3분 안에 접수하지 않으면 자동 취소. 취소·거부 2건 이상이면 당일 영업 임시 중지 | 도구 요약으로만 확인. 인용 전 링크 확인 필요 |

- 미접수 자동 취소와 매장 자동 차단은 여러 서비스에 공통으로 있다. 우리 쪽은 아직 정해지지 않았다(요청 문서 3.9절, 5장 질문 1·7).

## 부록: 용어 정리

회의에서 헷갈리기 쉬운 것만 적는다.

| 말 | 뜻 |
|---|---|
| pub/sub | 아이디어. 보내는 쪽은 주제에 던지고 구독한 쪽만 받는다 |
| MQTT | pub/sub를 주고받는 규칙(프로토콜) 중 하나. 브로커가 서버 → 매장 구간까지 맡는다 |
| Redis, RabbitMQ | pub/sub를 해 주는 제품. 서버끼리(회사 내부망) 쓰는 용도다. MQTT가 아니다 |
| SSE, WebSocket, 폴링 | 서버 → 매장(인터넷) 구간의 전달 방식. pub/sub와는 별개다 |

**구간이 둘이다.**

```
[서버 1] ─┐
[서버 2] ─┼─ [Redis 등]          ← 구간 1: 서버끼리 (SSE·WebSocket을 쓸 때 필요)
[서버 3] ─┘
    ║
    ╚══ SSE / WebSocket / 폴링 ══ [매장]   ← 구간 2: 서버 → 매장
```

| 조합 | 구간 1 (서버끼리) | 구간 2 (매장까지) |
|---|---|---|
| 짧은 폴링 | 필요 없음 | 폴링 |
| SSE 또는 WebSocket + Redis | Redis | SSE 또는 WebSocket |
| MQTT | 브로커가 담당 | 브로커가 담당 |

- SSE는 별도 서버 없이 기존 API 서버에 주소 하나를 추가해서 만들 수 있다. 연결 전담 서버를 따로 두는 것은 선택이다.

### 서버 구성 그림

실제 백엔드 구성은 확인 전이다. 아래는 일반적인 그림이며, 구성은 백엔드 팀이 정한다. 세 구성 모두 주기적 조회와 수신 확인이 함께 들어간다(그림에서는 생략).

**1. SSE, 서버 1대**

```
[고객 앱] ── 결제 ──▶ [API 서버] ══ SSE ══▶ [매장 프로그램]
                          │
                       [데이터베이스]
```

- API 서버가 주문을 저장하고, 자기가 들고 있는 SSE 연결로 매장에 바로 보낸다. Redis가 필요 없다.

**2. SSE, 서버 여러 대**

```
                          ┌──▶ [API 서버 1] ──┐
[고객 앱] ── 결제 ──▶ [입구] ─┤                 ├── [Redis] (서버끼리 알림)
                          └──▶ [API 서버 2] ══╪══ SSE ══▶ [매장 프로그램]
                                    │         │
                                 [데이터베이스] (공용)
```

1. 모든 API 서버가 Redis를 구독한다.
2. 매장이 SSE로 접속하면 입구(로드밸런서)가 서버 하나에 배정한다. 그 서버는 토큰으로 매장을 확인하고 "이 매장 연결은 내가 들고 있다"고 메모리에 적는다.
3. 결제를 처리한 서버(어느 서버든)가 주문을 저장하고 Redis에 "A매장 새 주문"을 발행한다.
4. 모든 서버가 그 알림을 받는다. A매장 연결을 들고 있는 서버만 SSE로 보내고, 나머지는 무시한다.

- SSE를 보내는 것은 API 서버다. Redis는 매장과 직접 통신하지 않고, 주문을 저장하지도 않는다.
- 각 서버는 자기에게 붙은 매장만 안다. "이 매장이 지금 접속 중인가"를 전체로 알려면 그 정보를 Redis나 DB에 따로 적어야 한다(3.9절의 주문 차단에 필요).
- 매장 PC 전원이 갑자기 꺼지면 서버가 끊김을 바로 모를 수 있다. 서버가 주기적으로 보내는 하트비트가 실패하면 그때 연결을 지운다.

**3. 짧은 폴링 (파일럿 의견)**

```
                          ┌──▶ [API 서버 1] ──┐
[고객 앱] ── 결제 ──▶ [입구] ─┤                 ├── [데이터베이스] (공용)
[매장 프로그램] ─ 3초마다 ─▶  └──▶ [API 서버 2] ──┘
   "새로 온 것 있어요?"
```

- 결제는 아무 서버나 받아 저장하고, 매장의 질문도 아무 서버나 데이터베이스를 보고 답한다. 서버가 몇 대든 Redis가 필요 없다.

| | 1. SSE, 서버 1대 | 2. SSE, 서버 여러 대 | 3. 짧은 폴링 |
|---|---|---|---|
| Redis | 필요 없음 | 필요 | 필요 없음 |
| 주문이 뜨는 속도 | 즉시 | 즉시 | 최대 3초 |
| 서버를 늘리면 | 2번 구성으로 바꿔야 함 | 그대로 | 그대로 |

### 서버가 "어느 매장이 어느 연결인지" 아는 방법 (SSE·WebSocket)

1. **매장 ID는 토큰에 들어 있다.** 기기를 등록할 때(요청 문서 3.1절) 백엔드가 "이 기기는 A매장 것"이라는 내용이 담긴 토큰을 발급하고, 매장 프로그램이 PC에 저장한다.
2. **접속할 때 토큰을 같이 보낸다.** 백엔드는 매장이 말하는 매장 ID를 믿지 않고, 자기가 발급한 토큰에서 매장 ID를 꺼낸다.
3. **서버가 표에 적는다.** 접속 요청 하나가 연결 하나다. 서버는 그 연결에 매장 ID를 붙여 메모리의 표에 넣는다.
4. **보낼 때 표에서 찾는다.** Redis에서 "A매장 새 주문" 알림이 오면 표에서 A매장 연결을 찾아 써 넣는다. 표에 없으면 무시한다.
5. **끊기면 표에서 지운다.**

서버가 여러 대면 표도 서버마다 따로 있다.

| | 서버 1의 표 | 서버 2의 표 |
|---|---|---|
| 들어 있는 매장 | B, D, E | A, C, F |

- "A매장이 어느 서버에 있는지"를 모아 둔 전체 표는 전달에는 필요 없다. 모든 서버가 Redis 알림을 받고 각자 자기 표를 보기 때문이다.
- 전체 정보가 필요한 것은 "A매장이 지금 접속 중인가"를 판단할 때다. 이때는 접속과 끊김을 Redis나 DB에 따로 적는다.

### 매장 프로그램이 받는 방식 (백엔드에 설명할 내용)

백엔드가 그대로 만들 수 있도록, 매장 프로그램이 무엇을 보내고 무엇을 기대하는지 적는다. 주소와 필드 이름은 제안이며 백엔드 기준에 맞춘다.

**공통**

| 항목 | 매장 프로그램의 동작 |
|---|---|
| 인증 | 모든 요청에 `Authorization: Bearer {기기 토큰}`을 붙인다. 401을 받으면 토큰을 재발급받고 다시 시도한다 |
| 매장 구분 | 백엔드가 토큰에서 매장 ID를 꺼내 그 매장 것만 준다. 주소의 매장 ID와 토큰의 매장 ID가 다르면 403 |
| 중복 | 같은 `eventId`를 두 번 받으면 두 번째는 무시한다 |
| 순서 | 주문의 `updatedAt`이 가지고 있는 것보다 오래되면 무시한다 |
| 수신 확인 | 주문을 화면에 띄운 뒤 `POST /orders/{orderId}/ack`를 보낸다 |
| 매장 → 백엔드 | 접수, 거절, 취소, 제조 완료, 픽업 완료는 REST API로 보낸다. 재전송에 대비해 `Idempotency-Key`를 붙인다 |

**짧은 폴링을 고를 경우**

```http
GET /stores/{storeId}/events?after={마지막으로 받은 eventId}
Authorization: Bearer {기기 토큰}

→ 200 { "events": [ ... ], "lastEventId": "evt_..." }
→ 200 { "events": [], "lastEventId": "evt_..." }     # 새 이벤트 없음
```

| 항목 | 매장 프로그램의 동작 | 백엔드에 필요한 것 |
|---|---|---|
| 주기 | 3초마다 호출한다 (주기는 협의) | 새 이벤트가 없을 때 가볍게 답한다 |
| 기준점 | 마지막으로 받은 `eventId`를 PC에 저장하고 `after`로 보낸다. 재시작해도 이어서 받는다 | `after` 이후 이벤트를 순서대로 준다 |
| 첫 실행 | `after` 없이 호출한다 | 처리 중인 주문(미접수·제조 중·준비 완료)을 준다 |
| 실패 | 응답이 없거나 오류면 다음 주기에 다시 묻는다. 계속 실패하면 화면에 "연결 끊김"을 띄운다 | — |
| 접속 신호 | 이 요청이 곧 "매장 프로그램이 켜져 있음" 신호다 | 마지막 요청 시각을 기록해 접속 여부를 판단한다 |

**SSE를 고를 경우**

```http
GET /stores/{storeId}/events
Accept: text/event-stream
Authorization: Bearer {기기 토큰}
Last-Event-ID: evt_...          # 재연결일 때만

→ 200 Content-Type: text/event-stream

id: evt_8f2a
event: ORDER_CREATED
data: { "order": { ... } }

: heartbeat
```

| 항목 | 매장 프로그램의 동작 | 백엔드에 필요한 것 |
|---|---|---|
| 이벤트 형식 | `id`를 `eventId`로, `event`를 종류로, `data`를 JSON으로 읽는다 | 이벤트마다 `id`를 붙인다 |
| 하트비트 | 일정 시간(예: 하트비트 주기의 2배) 동안 아무것도 오지 않으면 연결을 끊고 다시 붙는다 | 15~30초마다 주석 줄(`: heartbeat`)을 보낸다. 로드밸런서 유휴 타임아웃(기본 60초)보다 짧아야 한다 |
| 재연결 | 끊기면 간격을 늘려 가며 다시 붙고, 마지막으로 받은 `eventId`를 `Last-Event-ID`로 보낸다 | 가능하면 그 이후 이벤트를 다시 보낸다. 어렵다면 매장이 조회 API로 보충한다 |
| 재연결 직후 | 조회 API를 한 번 호출해 끊겨 있던 동안의 이벤트를 받는다 | 위 폴링용 조회 API를 함께 제공한다 |
| 연결 중 | 30~60초마다 조회 API를 호출해 빠진 이벤트가 없는지 확인한다 | — |
| 프록시 | — | 응답 버퍼링을 끈다(nginx는 `X-Accel-Buffering: no`) |
| 서버 여러 대 | — | 위 "서버 구성 그림" 2번처럼 서버끼리 알려 주는 장치를 둔다 |

- 두 방식 모두 조회 API(`GET .../events?after=`)가 필요하다. SSE를 고르면 조회 API에 SSE 주소가 하나 더 붙는 셈이다.
