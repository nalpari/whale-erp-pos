## 2. 처음 1분에 말할 것

1. 매장 PC에 설치하는 주문접수 프로그램을 만든다. 결제가 끝난 주문을 받아 접수하고 주문서를 출력한다.
2. 주문 누락 0건이 목표다. 그래서 전달 방식과 별개로 수신 확인, 주기적 조회, 중복 제거가 필요하다.
3. 오늘 정하고 싶은 것은 전달 방식, 담당, 조회 API 형태, 일정이다.

| 3 | "마지막으로 받은 이벤트 이후 것 전부"를 주는 조회 API를 만들 수 있나요? | 취소·변경 알림이 빠졌을 때 잡는 장치다. 안 되면 대안("최근 N분 안에 상태가 바뀐 주문")을 같이 정한다 |
| 4 | 매장 프로그램이 꺼져 있을 때 주문을 막거나 자동 취소하나요? | 결제는 됐는데 매장이 모르는 주문을 막아야 한다. 백엔드가 정할 일이 아니면 누가 언제까지 정하는지 받아 온다 |
| 5 | 스테이징 서버와 테스트 주문 API를 12월 중에 받을 수 있나요? | 늦어지면 연동 테스트 기간이 줄어 2월 파일럿 일정에 영향을 준다 |

## 4. 내 의견으로 말할 것

- **파일럿은 짧은 폴링(3초 간격)으로 시작하고 싶다.**
  - 백엔드가 새로 만들 것이 조회 API 하나다.
  - 이 요청 하나로 새 주문 수신, 고객 취소 수신, "매장 프로그램이 켜져 있음" 신호를 함께 처리한다.
  - 서버가 여러 대여도 문제가 없다. 어느 서버가 받아도 데이터베이스를 보고 답한다.
  - 대가는 최대 3초 지연이다. 전달 지연 목표를 "5초 이내"로 잡고 싶다.
- **수신 부분만 갈아 끼울 수 있게 만든다.** 매장이 늘면 다른 방식으로 바꿀 수 있다.
- **확장 단계 후보는 두 가지로 본다.**
  - SSE + Redis: 기존 HTTP 서버를 그대로 쓴다. 서버끼리 알려 주는 장치는 백엔드가 만든다.
  - MQTT + 느린 폴링(30~60초): 관리형 브로커가 연결과 라우팅을 맡는다. 새 서비스 계약과 매장별 인증 정보 관리가 필요하다.
  - 어느 쪽이든 폴링은 간격을 늘려 누락 방지용으로 남긴다.
- **매장에서 백엔드로 보내는 요청(접수, 거절, 취소 등)은 전부 REST API로 보낸다.**
- **취소·변경 정책 제안**: 고객 취소는 매장 접수 전까지만 받는다. 겹치면 백엔드가 먼저 도착한 쪽을 인정한다. 매장은 접수 성공 응답을 받은 뒤에만 주문서를 출력한다. 결제 후 메뉴 변경은 허용하지 않는다.

## 5. 예상 반문과 답

| 반문 | 답 |
|---|---|
| "폴링은 서버에 부담되지 않나요?" | 매장 1곳이면 3초에 1번, 100곳이어도 초당 약 33번이다. 주문이 없으면 "없음"만 답하면 된다 |
| "그냥 WebSocket으로 하죠." | 가능하다. 그러면 연결 서버, 하트비트, 서버 증설 때 라우팅을 백엔드에서 맡는지 확인한다. 조회 API는 그래도 필요하다 |
| "수신 확인은 왜 따로 하나요?" | 전달 방식은 "보냈다"까지만 알려 준다. 점원 화면에 떴는지는 매장이 알려 줘야 백엔드가 못 본 주문을 알 수 있다 |
| "3초 지연은 괜찮나요?" | 음료 제조에 분 단위가 걸리므로 괜찮다고 본다. 잘못 제조하는 일은 "접수 성공 후에만 출력" 규칙이 막는다 |
| "매장이 꺼졌는지 서버가 어떻게 아나요?" | 매장이 주기적으로 보내는 요청이 끊기면 꺼진 것으로 본다. 예: 30초 동안 요청이 없으면 "접속 안 됨". 기준 시간은 같이 정한다 |

## 부록: 용어 정리

회의에서 헷갈리기 쉬운 것만 적는다.

| 말 | 뜻 |
|---|---|
| pub/sub | 아이디어. 보내는 쪽은 주제에 던지고 구독한 쪽만 받는다 |
| MQTT | pub/sub를 주고받는 규칙(프로토콜) 중 하나. 브로커가 서버 → 매장 구간까지 맡는다 |
| Redis, RabbitMQ | pub/sub를 해 주는 제품. 서버끼리(회사 내부망) 쓰는 용도다. MQTT가 아니다 |
| SSE, WebSocket, 폴링 | 서버 → 매장(인터넷) 구간의 전달 방식. pub/sub와는 별개다 |

**구간이 둘이다.**

```
[서버 1] ─┐
[서버 2] ─┼─ [Redis 등]          ← 구간 1: 서버끼리 (SSE·WebSocket을 쓸 때 필요)
[서버 3] ─┘
    ║
    ╚══ SSE / WebSocket / 폴링 ══ [매장]   ← 구간 2: 서버 → 매장
```

| 조합 | 구간 1 (서버끼리) | 구간 2 (매장까지) |
|---|---|---|
| 짧은 폴링 | 필요 없음 | 폴링 |
| SSE 또는 WebSocket + Redis | Redis | SSE 또는 WebSocket |
| MQTT | 브로커가 담당 | 브로커가 담당 |

- SSE는 별도 서버 없이 기존 API 서버에 주소 하나를 추가해서 만들 수 있다. 연결 전담 서버를 따로 두는 것은 선택이다.

### 서버 구성 그림

실제 백엔드 구성은 확인 전이다. 아래는 일반적인 그림이며, 구성은 백엔드 팀이 정한다. 세 구성 모두 주기적 조회와 수신 확인이 함께 들어간다(그림에서는 생략).

**1. SSE, 서버 1대**

```
[고객 앱] ── 결제 ──▶ [API 서버] ══ SSE ══▶ [매장 프로그램]
                          │
                       [데이터베이스]
```

- API 서버가 주문을 저장하고, 자기가 들고 있는 SSE 연결로 매장에 바로 보낸다. Redis가 필요 없다.

**2. SSE, 서버 여러 대**

```
                          ┌──▶ [API 서버 1] ──┐
[고객 앱] ── 결제 ──▶ [입구] ─┤                 ├── [Redis] (서버끼리 알림)
                          └──▶ [API 서버 2] ══╪══ SSE ══▶ [매장 프로그램]
                                    │         │
                                 [데이터베이스] (공용)
```

1. 모든 API 서버가 Redis를 구독한다.
2. 매장이 SSE로 접속하면 입구(로드밸런서)가 서버 하나에 배정한다. 그 서버는 토큰으로 매장을 확인하고 "이 매장 연결은 내가 들고 있다"고 메모리에 적는다.
3. 결제를 처리한 서버(어느 서버든)가 주문을 저장하고 Redis에 "A매장 새 주문"을 발행한다.
4. 모든 서버가 그 알림을 받는다. A매장 연결을 들고 있는 서버만 SSE로 보내고, 나머지는 무시한다.

- SSE를 보내는 것은 API 서버다. Redis는 매장과 직접 통신하지 않고, 주문을 저장하지도 않는다.
- 각 서버는 자기에게 붙은 매장만 안다. "이 매장이 지금 접속 중인가"를 전체로 알려면 그 정보를 Redis나 DB에 따로 적어야 한다(3.9절의 주문 차단에 필요).
- 매장 PC 전원이 갑자기 꺼지면 서버가 끊김을 바로 모를 수 있다. 서버가 주기적으로 보내는 하트비트가 실패하면 그때 연결을 지운다.

**3. 짧은 폴링 (파일럿 의견)**

```
                          ┌──▶ [API 서버 1] ──┐
[고객 앱] ── 결제 ──▶ [입구] ─┤                 ├── [데이터베이스] (공용)
[매장 프로그램] ─ 3초마다 ─▶  └──▶ [API 서버 2] ──┘
   "새로 온 것 있어요?"
```

- 결제는 아무 서버나 받아 저장하고, 매장의 질문도 아무 서버나 데이터베이스를 보고 답한다. 서버가 몇 대든 Redis가 필요 없다.

| | 1. SSE, 서버 1대 | 2. SSE, 서버 여러 대 | 3. 짧은 폴링 |
|---|---|---|---|
| Redis | 필요 없음 | 필요 | 필요 없음 |
| 주문이 뜨는 속도 | 즉시 | 즉시 | 최대 3초 |
| 서버를 늘리면 | 2번 구성으로 바꿔야 함 | 그대로 | 그대로 |

- 근거와 출처는 `docs/research/store-order-receiver-tech-research.md` 6~7장과 `docs/reviews/2026-11-16-docs-verification.md`에 있다.
