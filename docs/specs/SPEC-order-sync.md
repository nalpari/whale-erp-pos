## 1. 목표

서버에서 결제가 끝난 주문을 **빠짐없이, 한 번씩만** 받아 프로그램 안에 보관하고, 점원이 누른 상태 변경을 서버에 보낸다. 다른 PC · 고객 · 서버가 바꾼 상태도 화면에 맞춘다. 주문 화면(T04~T07)은 이 모듈이 가진 주문 목록을 보여 주기만 한다.

- **이번 범위**
  - 주문 수신 · 보관 · 재조회 · 중복 방지 · 상태 변경 요청 (화면 없음)
  - T01에서 넘어온 것: 인터넷 끊김 빨간 띠 · 경고음, 더보기 [새로고침], 확인창의 "처리할 주문 N건"에 실제 건수 넣기
  - 서버가 주문받기를 자동으로 끌 때의 헤더 처리와 빨간 띠 (Q53 · Q54)
  - 모든 서버 요청에 시간 제한 10초
  - 개발 빌드 전용 "모의 주문" 버튼
- **이번 범위 밖**: 주문 카드 화면(T04), 요약 팝업 · 주문취소 팝업(T05), 위젯 · 30초 반복 알림음(T06), 주문내역(T07), 주문서 출력(T12), 실제 API(T17). 이 모듈은 그 화면들이 쓸 값과 신호만 준다.

### 2.1 상태가 바뀌는 길

| 지금 | 누름 / 사건 | 다음 | 누가 |
|---|---|---|---|

| 접수대기 | 고객 취소 | 고객취소 | 고객 (Q19, 접수대기일 때만) |
| 접수대기 | 15분 미접수 | 매장취소(자동) | 서버 (Q20) |

- 제조완료 · 픽업완료부터는 매장 프로그램에서 취소할 수 없다 (Q17).
- 이 표에 없는 변경 요청은 보내지 않는다. 화면에서 그 버튼을 보이지 않는 것은 T04 · T05가 맡지만, 이 모듈도 막는다.

## 3. 동작

### 3.1 받기

1. 로그인에 성공하면 수신을 시작하고, 로그아웃 · 프로그램 종료 때 멈춘다.
2. 시작할 때 **처리할 주문 전체**(접수대기 · 제조중 · 제조완료)와 **오늘 픽업완료**를 서버에서 한 번 조회해 목록을 채운다. 다시시작 · 다시 연결 · [새로고침]도 같다.
3. 그 뒤로는 실시간 연결로 들어오는 사건(새 주문 · 상태 변경 · 주문받기 변경)을 반영한다. 실시간 전달 방식은 백엔드 미정이므로 **수신 부분만 바꿔 끼울 수 있게** 나눈다 (`OrderFeed` 인터페이스, 5장).
4. 실시간 연결과 따로 **30초마다** 처리할 주문을 다시 조회해 빠진 것을 잡는다 (사용자 결정 E-1, 실제 값은 백엔드 회의 뒤 다시 정함).
5. 새 주문을 목록에 넣은 뒤 서버에 수신 확인(ack)을 보낸다. ack가 실패하면 다음 조회 때 다시 보낸다.

### 3.2 중복 · 순서

1. 같은 `orderId`의 새 주문이 두 번 오면 한 번만 넣고, "새 주문" 신호(알림음 · 위젯 · 출력이 쓰는 것)도 한 번만 낸다.
2. 이벤트에 `eventId`가 있으면 처리한 것을 기억해 다시 오면 버린다. 기억은 최근 1,000개까지만 둔다(며칠 켜 두어도 메모리가 늘지 않게).
3. 가지고 있는 것보다 오래된 `updatedAt`(또는 버전)의 내용은 버린다. 조회 결과와 실시간 이벤트가 엇갈려도 최신만 남는다.
4. 다시시작 뒤 첫 조회로 들어온 주문은 "새 주문" 신호를 내지 않는다. 이미 보였던 주문일 수 있어서다. 접수대기 주문이 있으면 반복 알림(T06)이 따로 알린다. (11장 G)

### 3.3 상태 변경 요청

1. 요청마다 멱등키를 붙인다. 같은 누름을 다시 보내도(시간 초과 뒤 재시도 등) 서버에서 한 번만 처리된다.
2. **서버가 성공을 돌려준 뒤에만** 목록의 상태를 바꾸고, 그 뒤에 "접수됨" 신호(주문서 출력 T12가 씀)를 낸다. 화면이 먼저 바뀌는 낙관적 갱신은 하지 않는다.
3. 같은 주문에 요청이 진행 중이면 그 주문의 다른 요청은 받지 않는다(두 번 누름 방지).
4. 결과별 처리

| 서버 응답 | 목록 | 화면에 줄 문구 (T04 · T05가 보임) | 근거 |
|---|---|---|---|
| 성공 | 새 상태로 | 없음 | |
| 다른 PC가 먼저 처리 | 서버가 준 최신 상태로 | 「다른 PC에서 이미 처리한 주문입니다.」 | Q13 |
| 고객이 먼저 취소 | 고객취소로 | 「고객이 이미 취소한 주문입니다.」 | Q19 |
| 서버 오류 · 시간 초과 · 인터넷 끊김 | 그대로 | 「처리하지 못했습니다. 잠시 뒤 다시 시도해 주세요.」 | Q51 ② |

### 3.4 연결 상태와 빨간 띠

1. 15초마다 서버에 연결 신호(heartbeat)를 보낸다 (Q53의 15~20초 중 짧은 쪽).
2. 연결 상태는 `연결됨 · 다시 연결 중` 둘이다. 실시간 연결이 끊기거나 연결 신호 · 조회가 연달아 2번 실패하면 `다시 연결 중`으로 본다. (11장 H)
3. `다시 연결 중`이 되면 헤더 아래에 빨간 띠 「인터넷 연결이 끊겼습니다. 새 주문을 받을 수 없습니다. 다시 연결하는 중…」을 띄우고 경고음을 **한 번** 낸다 (Q51 ①). 띠는 닫을 수 없다.
4. 다시 연결을 시도하는 간격은 1초 → 2초 → 4초 … 최대 30초로 늘린다.
5. 다시 연결되면 띠를 지우고, 3.1의 2번처럼 전체를 다시 조회한다. 주문받기는 끊기기 직전 상태로 둔다 (Q51 · Q53, 11장 I).

### 3.5 서버가 주문받기를 바꿀 때

1. 서버가 보낸 "주문받기 변경" 사건은 확인창 없이 헤더 토글에 반영한다. 다른 PC에서 바꾼 것도 같다 (Q13: 점포 단위).
2. 이유가 "미접수 자동 취소 연속 2건"이면 헤더 아래 빨간 띠 「접수하지 않은 주문 2건이 자동 취소되어 주문받기가 꺼졌습니다. 주문을 받으려면 주문받기를 켜 주세요.」를 띄우고 새 주문 알림음을 한 번 낸다. 띠는 주문받기를 켤 때까지 남는다 (Q54). 위젯 안내 카드는 T06.
3. 로그인 직후 서버의 주문받기 상태를 조회해 맞춘다. 다만 프로그램을 켤 때는 OFF로 시작하는 규칙(Q03)이 우선이라, 서버가 ON이면 OFF 요청을 보낸다. (11장 J)
4. 띠가 두 개 이상이면 위로 쌓는다. 순서는 인터넷 끊김 → 자동 OFF.

### 3.6 시간 제한 (사용자 결정 C-1)

- 모든 서버 요청은 **10초** 안에 응답이 없으면 실패로 본다. 로그인 · 주문받기 · 주문 조회 · 상태 변경 · ack · 연결 신호가 모두 해당한다.
- 로그아웃 · 다시시작 · 프로그램 종료 전 "주문 중단" 요청도 10초가 지나면 그대로 진행한다 (T01의 "실패해도 진행"과 같음).
- 실패 문구는 3.3 표와 같다. 로그인 화면은 로그인 스펙의 네트워크 오류 문구를 그대로 쓴다.

## 8. 테스트 전략

- `orders-state.ts` 순수 함수: 상태 변경 표(허용 · 거부), 중복 주문 · 중복 이벤트, 오래된 이벤트 버림, 처리할 주문 건수.
- `OrdersProvider`: 가짜 `OrderApi` · `OrderFeed`와 가짜 시계로
  - 주문 100건을 섞인 순서 · 중복 포함으로 보내도 목록 100건, "새 주문" 신호 100번
  - 끊김 → 빨간 띠 · 경고음 한 번 → 다시 연결 → 띠 사라짐 · 전체 재조회 · 끊긴 동안의 주문이 들어옴
  - 상태 변경 성공 / 다른 PC 먼저 / 고객 먼저 / 서버 오류 / 시간 초과(10초) 각각의 목록과 문구
  - 같은 주문 두 번 누름은 요청 한 번
  - 서버 주문받기 자동 OFF(연속 2건) → 토글 OFF · 띠 · 알림음, 켜면 띠 사라짐
  - 30초 재조회가 빠진 주문을 채운다
- 운영 빌드에 모의 버튼 코드가 없는지 빌드 결과물에서 확인한다.

## 9. 경계

- **항상**: 서버 성공 뒤에만 상태 변경 · 출력 신호. 로그에는 `orderId`만.
- **먼저 묻기**: 새 라이브러리, 이 스펙에 없는 상태 변경, 실시간 방식을 정하는 일.
- **하지 않기**: 주문 카드 · 팝업 · 위젯 화면, 알림음 반복, 출력, 실제 API 연결.

## 10. 완료 기준

1. 모의 서버로 주문 100건을 섞인 순서 · 중복 포함으로 보내도 빠짐 · 중복 0건, "새 주문" 신호는 주문마다 한 번 (테스트).
2. 다시시작 · 다시 연결 · [새로고침] 뒤 끊긴 동안 결제된 주문이 들어온다 (테스트 + 모의 버튼으로 수동).
3. 상태 변경은 서버 성공 뒤에만 바뀌고, 3.3 표의 실패 4종이 표대로 처리된다 (테스트).
4. 인터넷 끊김 띠 · 경고음 한 번, 다시 연결 뒤 띠가 사라지고 주문받기가 직전 상태다 (테스트 + Linux 실제 창).
5. 서버 자동 OFF(연속 2건) 때 토글 OFF · 띠 · 알림음, 켜면 띠가 사라진다 (테스트).
6. 모든 서버 요청이 10초 뒤 실패로 끝나고, 종료 전 "주문 중단"이 10초 뒤 그대로 진행된다 (테스트).
7. 확인창 경고 줄에 실제 건수가 나온다 (테스트).
8. 운영 빌드에 모의 버튼이 없다. ① lint · typecheck · format · test · build · Rust 검사 통과, ② · ③ 리뷰 완료.

## 12. 개정 (2026-11-25 대표님 결정 + Q60~Q69 답, 2026-11-25 사용자 승인)

- **T18 취소 범위**: 2.1 표의 [주문취소] 줄을 「접수대기 · 제조중 · 제조완료 · 픽업완료(결제한 날 0시 전)」 → 매장취소로 넓힌다. 「제조완료 · 픽업완료부터는 매장 프로그램에서 취소할 수 없다 (Q17)」 → 「결제한 날 0시가 지난 픽업완료와 취소된 주문은 취소할 수 없다. 0시 판단은 서버가 한다」. 고객 취소는 접수대기에서만(그대로). `SPEC-order-summary.md` 12장.
- **T22 「환불」 상태**: 상태에 **환불**을 더한다. 매장취소 · 고객취소(자동 취소 포함) 주문의 환불이 끝나면 서버가 「환불」로 바꾸고 주문 변경으로 알린다(Q66). 누가 취소했는지는 취소 정보에 그대로 남는다. 매장 프로그램이 「환불」로 바꾸는 요청은 없다.
