# 스펙: 재제조 (`remake`)

- **태스크**: T21 (Plane WHALEERPPO-54)
- **근거**: 기획자 답변 Q62 · Q64와 담당자 결정 (2026-11-25, `docs/tasks/planner-answers.md` 끝), 요약 팝업 스펙 `SPEC-order-summary.md` 12장, 출력 스펙 `SPEC-print-forms.md`
- **선행**: T05 요약 팝업, T07 주문내역 상세, T12 출력. T18과 같은 버튼 표를 쓰므로 T18 뒤에 한다.
- **상태**: 승인 (2026-11-25, 사용자)

## 1. 목표

잘못 만들었거나 고객이 다시 만들어 달라고 할 때, 점원이 [재제조]를 눌러 사유를 남기고 「[재제조]」 주문서를 다시 뽑는다. 주문 상태와 금액은 바뀌지 않는다.

- **이번 범위 밖**: 재제조 비용 부담(Q68 답 대기), 재제조 통계 화면, 고객 알림.

## 2. 누르는 곳 · 때

- 요약 팝업과 주문내역 상세의 [재제조] 버튼. 위젯에는 두지 않는다.
- **제조완료**, 그리고 **결제한 날 0시 전의 픽업완료** 주문에서 보인다(`SPEC-order-summary.md` 12장 표). 0시 판단은 서버가 한다.
- 로그인한 계정이면 누구나 누를 수 있다 (Q64).
- 버튼은 강조하지 않는다([주문취소]와 같은 회색 테두리). 높이 44px 이상.

## 3. 재제조 팝업

| 번호 | 요소 | 내용 |
|---|---|---|
| 1 | 제목 | 「재제조하시겠습니까?」 |
| 2 | 다시 만들 메뉴 | 주문의 메뉴마다 한 줄(메뉴명 + 옵션 한 줄 + 주문 수량). 줄마다 체크칸과 수량 고르기(1 ~ 그 메뉴의 주문 수량, − / + 버튼 44px 이상). 처음에는 모두 체크 해제, 체크하면 수량은 주문 수량으로 시작한다 |
| 2-1 | 사유 (하나 고름) | 메뉴를 잘못 만들었습니다 / 맛 · 품질 문제 / 이물질 / 고객 주문 실수 / 직접 입력 |
| 3 | 직접 입력 | 「직접 입력」을 고르면 글칸이 열린다. 50자, 줄바꿈 없음 (취소 팝업과 같은 규칙) |
| 4 | 버튼 | [닫기] [재제조★] |

- 메뉴를 하나도 고르지 않았거나, 사유를 고르지 않았거나, 직접 입력이 비어 있으면 [재제조]가 막힌다.
- 메뉴 선택은 재고를 맞추려는 것이다. 서버가 고른 메뉴 · 수량만큼 재고를 뺀다고 가정한다(재고 계산은 서버 몫, 2026-11-26 사용자 결정).
- 사유 목록은 2026-11-25 지휘 세션 초안이다. 나중에 더한다(담당자 결정). 목록은 상수 하나로 둔다.
- 「고객 주문 실수」는 Q62의 「고객 실수로 인한 재제조」, 나머지는 「실제 클레임」에 해당한다. 서버에는 사유 문구와 함께 이 구분(매장 과실 / 고객 실수)을 보낸다고 가정한다.

## 4. 동작

1. [재제조]를 누르면 서버에 재제조 요청(주문 ID, 고른 메뉴와 수량 목록, 사유, 구분, 멱등키)을 보낸다. 요청 중에는 버튼을 막고 진행 표시를 한다.
2. 서버가 성공을 돌려주면 팝업을 닫고 「#12 재제조를 등록했습니다.」 토스트를 띄운다.
3. 같은 PC에서 「주문서」가 체크된 프린터 모두로 **「[재제조]」 주문서**를 뽑는다(`SPEC-print-forms.md` 13장). 출력 실패 처리는 주문서 실패 규칙(Q47)과 같다.
4. 주문 상태는 바뀌지 않는다. 픽업완료 주문이면 [픽업완료] 탭에 그대로 있다.
5. 같은 주문에 재제조를 여러 번 할 수 있다. 할 때마다 기록이 하나씩 쌓인다.

## 5. 실패

- 서버 오류 · 인터넷 끊김 · 10초 무응답: 팝업을 닫지 않고 「처리하지 못했습니다. 잠시 뒤 다시 시도해 주세요.」 (PL WIN-05). 주문서는 뽑지 않는다.
- 그사이 주문이 취소됐거나 0시가 지나 서버가 거절하면 팝업을 닫고 「#12 재제조할 수 없는 주문입니다.」 토스트, 화면은 서버의 최신 상태로 맞춘다.

## 6. 기록 보기

- 주문내역 상세 처리 이력에 재제조마다 「재제조 HH:mm · 사유」 줄과 고른 메뉴 · 수량을 더한다(`SPEC-order-history.md` 12.3).
- 요약 팝업에는 기록을 보이지 않는다.

## 7. 데이터 (가정, 백엔드 협의 전)

- 서버에 보냄: 주문 ID, 다시 만들 메뉴 목록(주문 메뉴 줄을 가리키는 값 + 수량), 사유 문구, 구분(매장 과실 / 고객 실수), 멱등키. 주문 설계(DC-ORDFLH)의 클레임 대상 품목 · 수량과 맞춘다.
- 서버에서 받음: 성공 / 실패와 실패 종류, 주문 상세의 재제조 기록 목록(시각 · 메뉴와 수량 · 사유 · 구분). 재고 부족 등으로 서버가 거절하면 5장의 거절과 같이 처리한다.
- 주문 설계 쪽(DC-ORDFLH)의 클레임 REMAKE와 맞춘다. 지금 그 문서는 재제조를 고객센터가 등록한다고 적고 있어 알려야 한다(고객센터는 없음).

## 9. 로그

- 남길 것: 재제조 요청 · 성공 · 실패(주문 ID, 구분, 사유 번호). 직접 입력한 글은 남기지 않는다.
- 남기지 않을 것: 고객 이름 · 연락처.

## 10. 완료 기준

1. 제조완료 · 그날 픽업완료에서 [재제조]가 보이고, 지난 날 픽업완료 · 다른 상태에서는 보이지 않는다 (테스트).
2. 사유를 고르지 않으면 [재제조]가 막히고, 직접 입력은 50자 · 줄바꿈 없음 (테스트).
3. 성공하면 「[재제조]」 주문서가 「주문서」 프린터로 나가고 상태는 그대로다 (테스트 + 개발 출력 미리보기).
4. 실패하면 주문서를 뽑지 않고 안내가 뜬다 (테스트).
5. 주문내역 상세에 재제조 기록이 보인다 (테스트).
6. ① lint · typecheck · format · test · build · Rust 검사 통과, ② · ③ 리뷰 완료.
