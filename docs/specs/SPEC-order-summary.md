## 1. 목표

주문 카드를 누르면 주문 한 건을 자세히 보여 주고, 그 자리에서 다음 단계 처리와 주문취소를 한다. 취소 사유 팝업은 위젯(T06)도 같이 쓴다 (Q17 · Q33).

- **이번 범위 밖**: 실제 인쇄(T12, 버튼 자리만), 위젯에서 여는 것(T06), 주문내역 상세(T07, 같은 버튼 규칙을 쓴다 · Q27), 취소 영수증(T12 · Q50).

## 2. 주문 요약 팝업 (p.12)

### 2.1 여닫기

- 여는 법: [주문접수] 화면의 카드(버튼 밖)를 누른다. T04가 비워 둔 `onOpen` 자리에 연결한다.
- 닫는 법: × 버튼, 어두운 바깥 영역 누르기, Esc.
- 한 번에 하나만 연다.

### 2.2 구성

| 번호 | 요소 | 내용 |
|---|---|---|
| 1 | 머리 | 픽업번호 `#12`, 현재 상태 글자, × |
| 2 | 처리 단계 | 접수대기 → 제조중 → 제조완료 → 픽업완료 (Q16, 「제조시작」 단계 없음). 지난 단계는 체크 + 시각(시:분), 현재 단계는 강조. 픽업완료 상태면 모든 단계에 체크 + 시각 (11장 B · F) |
| 3 | 기본 정보 | 주문일시(결제 시각), 주문번호 16자리(Q28), 픽업 예정(카드와 같은 문구 · T04 2.4), 고객명(가린 값), 연락처(끝 4자리만 · 11장 E) |
| 4 | 요청사항 | 있으면 노란 바탕으로 전체(말줄임 없음). 없으면 칸을 두지 않는다 |
| 5 | 메뉴 목록 | 메뉴명 · 수량, 옵션은 그 아래 쉼표로 한 줄씩 이어서 전체(말줄임 없음). 메뉴가 많으면 팝업 안에서 세로 스크롤 |
| 6 | 인쇄 · 취소 버튼 | [영수증 인쇄] [주문서 인쇄] [주문취소] (2.3) |
| 7 | 다음 단계 버튼 | 파란색 강조 하나 (2.3) |

### 2.3 상태별 버튼 (Q27)

| 상태 | 상태 버튼 (★ 파란 강조) | 인쇄 버튼 |
|---|---|---|
| 접수대기 | [주문취소] [주문접수★] | [영수증 인쇄], [주문서 인쇄]는 막힘 |
| 제조중 | [주문취소] [제조완료★] | [영수증 인쇄] [주문서 인쇄] |
| 제조완료 | [픽업완료★], [주문취소]는 막힘 | [영수증 인쇄] [주문서 인쇄] |
| 픽업완료 | 없음 | [영수증 인쇄] [주문서 인쇄] |

- [주문취소]는 강조하지 않는다 (바쁠 때 잘못 누르지 않게, Q27).
- 인쇄 버튼은 T12 전까지 11장 A대로 둔다. → T12에서 연결함(2026-11-19, `SPEC-print-forms.md`).
- 버튼은 높이 44px 이상.

### 2.4 버튼 동작

1. 다음 단계 버튼은 T04 카드 버튼과 같은 길로 간다: `useOrders().changeStatus`, 요청 중 막기, 실패하면 「#12 …」 토스트 (T04 2.6 · 11장 J).
2. 성공하면 팝업은 열린 채로 새 상태로 바뀐다(단계 표시 · 버튼). [픽업완료]가 성공하면 팝업을 닫고 T04의 픽업완료 배너 5초 + [완료 취소]가 뜬다 (11장 D).
3. [주문취소]는 취소 사유 팝업(3장)을 요약 팝업 위에 연다.

### 2.5 열려 있는 동안 주문이 바뀌면

- 다른 PC가 처리하거나 서버가 바꾸면 팝업 내용이 바로 새 상태로 바뀐다 (T03 목록을 그대로 본다).
- 매장취소 · 고객취소 · 자동취소로 목록에서 사라지면 팝업(과 취소 사유 팝업)을 닫는다. 고객 취소면 T04의 고객 취소 배너가 그대로 뜬다 (11장 C).

## 3. 주문취소 팝업 (p.7 · Q17 · Q18)

| 요소 | 내용 |
|---|---|
| 제목 | 「주문을 취소하시겠습니까?」 |
| 안내 | 「취소사유를 선택하세요.」 |
| 사유 (하나 선택) | 1 「재료가 소진되었습니다」 · 2 「주문이 많아 준비가 어렵습니다」 · 3 「영업이 종료되었습니다」 · 4 「매장 사정으로 주문을 취소합니다」 · 5 「직접 입력」 |
| 직접 입력 칸 | 5를 고르면 쓸 수 있다. 50자까지, 줄바꿈 없음, 칸 아래 「입력한 사유는 고객에게 보입니다.」 |
| 버튼 | [닫기] [주문취소] |

- 처음 열면 아무것도 선택되지 않는다. 사유를 골라야(직접 입력이면 공백 아닌 글자가 있어야) [주문취소]가 눌린다 (Q18).
- 글자 수는 보이는 글자 하나를 1자로 센다(이모지 · 띄어쓰기 포함, Q40). 붙여넣기로 넘으면 50자까지만 넣고 「50자까지 입력할 수 있습니다.」를 보인다.
- 처음 초점은 [닫기]. Esc · [닫기]로 닫으면 요약 팝업으로 돌아간다. 바깥 영역을 눌러도 닫히지 않는다(잘못 닫아 사유를 다시 고르는 일 방지).
- [주문취소]를 누르면 `changeStatus(orderId, "cancel", 사유 문구)`. 요청 중엔 두 버튼을 잠근다.
  - 성공: 두 팝업을 닫는다. 카드는 T03이 목록에서 지워 사라진다.
  - 실패: 취소 사유 팝업을 닫지 않고(고른 사유 유지) 「#12 …」 토스트를 보인다. 고객이 먼저 취소했으면 2.5대로 닫힌다.
- 서버로 보내는 사유는 고른 문구 그대로(직접 입력은 앞뒤 공백을 지운 값). 고객 앱 문구는 서버가 만든다 (Q17).
- 이 팝업은 T06 위젯도 쓰므로 주문 하나(`orderId`)만 받아 동작하게 만든다.

## 5. 로그

- 남길 것: 상태 변경 결과는 T03이 남긴다(orderId · 동작 · 결과).
- 남기지 않을 것: 취소 사유 원문(직접 입력은 개인정보가 섞일 수 있다), 고객명 · 연락처 · 요청사항.

## 6. 테스트 전략

- `summary-logic.ts`: 4개 상태 × 버튼 표(Q27), 단계 표시, 사유 검사(미선택 · 직접 입력 공백 · 50자 · 이모지 1자).
- 화면: 카드를 누르면 열림, ×/바깥/Esc 닫힘, 상태별 버튼 · 막힘, 다음 단계 성공 시 팝업 갱신, [픽업완료] 성공 시 닫힘 + 배너, 실패 토스트, 취소 팝업 사유 선택 전 막힘, 취소 성공 시 두 팝업 닫힘 · 카드 사라짐, 취소 실패 시 사유 유지, 열린 동안 다른 PC 처리 → 갱신, 고객 취소 → 닫힘 + 배너.

## 7. 경계

- **항상**: 상태 변경은 `useOrders().changeStatus`로만. 개인정보는 서버가 가린 값만.
- **먼저 묻기**: 새 라이브러리, 이 스펙에 없는 버튼 · 문구.
- **하지 않기**: 실제 인쇄, 위젯, 주문내역 상세.

## 8. 완료 기준

1. 카드를 누르면 요약 팝업이 열리고 ×/바깥/Esc로 닫힌다 (테스트).
2. 4개 상태마다 단계 표시와 버튼이 2.3 표와 같다. 제조완료 · 픽업완료에서 [주문취소]가 눌리지 않는다 (테스트).
3. 다음 단계 버튼이 동작하고, [픽업완료]면 팝업이 닫히고 배너가 뜬다 (테스트).
4. 사유를 고르거나 입력해야만 취소가 진행되고, 서버 성공 뒤 두 팝업이 닫히고 카드가 사라진다. 실패면 사유를 유지한 채 토스트 (테스트).
5. 열려 있는 동안 다른 PC 처리 · 고객 취소가 2.5대로 반영된다 (테스트).
6. 터치로 버튼 · 사유 선택 · 직접 입력이 된다 (Linux 실제 창 + Windows 수동).
7. ① lint · typecheck · format · test · build · Rust 검사 통과, ② · ③ 리뷰 완료.
