- **태스크**: T04 (Plane WHALEERPPO-5, `[F-ORDBRD]`), 태스크 문서 `docs/tasks/T04-order-board.md` (기획자 답변 전에 쓴 것이라 이 스펙이 우선한다)

## 1. 목표

[주문접수] 탭에서 들어온 주문을 카드로 보여 주고, 카드의 버튼으로 접수 · 제조완료 · 픽업완료를 처리한다. 점원이 하루 종일 보는 화면이다.

- **사용자**: 매장 점원(바쁨, 터치 우선), 점주.
- **이번 범위 밖**: 주문 요약 팝업 · 주문취소 사유 팝업(T05), 위젯 · 30초 반복 알림음(T06), 주문서 출력 · 「미출력」 꼬리표 · 출력 실패 띠(T12), 실제 소리 파일(T06). 주문 목록 · 상태 변경 요청 · 실패 문구는 T03이 이미 준다(`useOrders()`).

## 2. 화면 구성

### 2.1 탭과 정렬 (Q01 · Q21)

| 탭 | 보이는 주문 | 정렬 |
|---|---|---|
| [접수대기 · 제조중 · 제조완료] (기본) | 접수대기 · 제조중 · 제조완료 | [최신순 ▼] 선택칸: 최신순(기본) / 오래된순. 고른 값은 PC에 저장해 다시 켜도 유지 (Q15) |
| [픽업완료] | 오늘(PC 시계 0시 이후) 결제한 주문 중 픽업완료된 것 (11장 H) | 최신순만 |

- 정렬 기준은 카드에 보이는 주문시간(결제 시각)이다.
- 매장취소 · 고객취소 주문은 카드로 보이지 않는다 (Q17 · Q19, 주문내역 T07에서 본다).
- 0시가 지나면 [픽업완료] 탭이 비워진다. 0시 자동 픽업완료(Q21)는 서버가 하고, 화면은 받은 변경을 그대로 보인다.

### 2.2 보기 필터 (Q01 ③)

- 첫 탭에만 둔다: ☑접수대기 N ☑제조중 N ☑제조완료 N. 처음엔 모두 체크.
- 체크를 풀면 그 상태 카드를 숨긴다. 건수는 숨겨도 계속 보인다.
- 필터 상태는 저장하지 않는다(켤 때마다 모두 체크). (11장 D)

### 2.3 카드 (Q24 · Q25 · Q26)

| 줄 | 내용 |
|---|---|
| 머리 | 픽업번호 `#12`(앞자리 0 없음), 상태 글자, 카드 오른쪽 위 `›` |
| 시간 | 주문시간 `13:10` · 가린 고객명 · 픽업 예정 (2.4) |
| 메뉴 | 메뉴명 + 수량, 3줄까지. 넘으면 「+ 외 N개」(N = 남은 메뉴 종류 수). 메뉴마다 옵션은 그 아래 한 줄, 넘으면 말줄임(…) — 옵션 줄은 3줄에 세지 않는다 |
| 요청사항 | 있으면 노란 바탕 2줄, 넘으면 말줄임. 없으면 칸을 두지 않는다 |
| 경고 | 접수대기가 결제 뒤 12분부터 빨간 글자 「3분 뒤 자동 취소」 (Q20, 11장 C) |
| 버튼 | 접수대기 [주문접수] · 제조중 [제조완료] · 제조완료 [픽업완료] · 픽업완료 없음 |

- 카드 높이는 모두 같다. 폭은 약 300px.
- 카드 색(화면정의서 p.11 그림): 접수대기 노랑, 제조중 파랑, 제조완료 초록, 픽업완료 회색. 색만으로 구분하지 않고 상태 글자도 함께 보인다.
- 버튼은 높이 44px 이상 (Q23 · 터치 우선).
- 거부 버튼은 카드에 두지 않는다. 취소는 [주문취소] 하나로 요약 팝업에서 한다 (Q17, T05).
- 카드(버튼 밖)를 누르면 요약 팝업을 연다 (T05, 11장 A).

### 2.4 픽업 예정 표시 (Q26)

| 고객이 고른 값 | 카드 표시 (예: 15:25 결제) |
|---|---|
| 지금 | 「지금 픽업」, 결제 뒤 시간이 지나면 「지금 픽업 (3분 지남)」 |
| 5 · 10 · 20 · 30 · 40분 | 「15:45 픽업 (20분 뒤)」, 괄호 안이 1분마다 줄어든다 |
| 1시간 이상 | 「16:25 픽업 (1시간 이상)」 (결제 시각 + 1시간) |
| 예정 시각이 지남 | 괄호 안을 빨간 글자 「3분 지남」 |

- 1분마다 다시 계산한다. 화면 전체를 다시 그리지 않고 시간 글자만 바꾼다(주문이 많아도 멈추지 않게).
- "지금" · "1시간 이상"을 구분하려면 주문 데이터에 고객이 고른 값이 있어야 한다 (11장 B).

### 2.5 배치와 이전 / 다음 버튼 (Q23)

- 카드는 왼쪽 위부터 오른쪽으로, 줄이 차면 아래 줄로. 창 폭에 맞춰 한 줄에 들어가는 만큼(1024 → 3장, 1280 → 4장, 1920 → 6장).
- 세로는 손가락 끌기 · 마우스 휠로 스크롤한다.
- 카드가 한 화면을 넘을 때만 오른쪽 아래에 [이전] [다음] 버튼을 보이고, 한 번에 한 화면 분량씩 넘긴다.

### 2.6 버튼 동작

1. 버튼을 누르면 `useOrders().changeStatus`를 부른다. 그 주문이 "요청 중"이면 버튼을 막고 누른 버튼에 진행 표시를 한다.
2. 성공하면 카드가 새 상태로 바뀐다(T03이 서버 성공 뒤에만 목록을 바꾼다). 주문서 출력은 T03의 "접수됨" 신호로 T12가 한다.
3. 실패하면 T03이 준 문구를 공용 Toast로 보이고, 앞에 「#픽업번호 」를 붙인다(예: 「#12 다른 PC에서 이미 처리한 주문입니다.」, 11장 J): 「다른 PC에서 이미 처리한 주문입니다.」 · 「고객이 이미 취소한 주문입니다.」 · 「처리하지 못했습니다. 잠시 뒤 다시 시도해 주세요.」

### 2.7 화면 아래 배너 (Q19 · Q22)

| 배너 | 내용 | 사라지는 때 |
|---|---|---|
| 픽업완료 | 「픽업번호 #77 픽업완료 되었습니다.」 + [완료 취소(05)] (5초 카운트다운) | 5초 뒤 |
| 고객 취소 | 「픽업번호 #343 고객이 주문을 취소했습니다.」 + 새 주문 알림음 한 번 | 5초 뒤 |

- [픽업완료]가 서버에서 성공한 뒤 배너를 띄운다. [완료 취소]는 T03의 되돌리기 요청을 보내고, 성공하면 카드가 제조완료로 돌아온다. 실패하면 2.6의 실패 문구.
- 5초가 지나기 전까지 그 카드는 첫 탭에 남고, 지나면 [픽업완료] 탭으로 간다 (Q21).
- 고객 취소 배너는 접수대기였던 주문이 고객취소로 바뀌는 것을 보고 띄운다. 처음 조회 때 이미 고객취소인 주문에는 띄우지 않는다.
- 배너가 여럿이면 위로 쌓고 새 배너가 맨 아래에 붙는다. 각각 따로 사라진다. 출력 실패 빨간 띠도 같은 자리에 쌓인다(T12).
- 배너는 [주문접수] 탭에서만 보인다. 다른 탭에 있을 때 생긴 배너는 보이지 않는다 (11장 E). 고객 취소 알림음은 다른 탭에 있어도 한 번 울린다 (11장 I).
- 연결이 끊긴 사이 고객이 취소한 주문은 재연결 뒤 전체 조회로 맞춰질 때 배너 · 알림음 없이 카드만 사라진다 (11장 G).

### 2.8 비었을 때

- 첫 탭에 주문이 없으면 가운데에 「처리할 주문이 없습니다.」, [픽업완료] 탭은 「오늘 픽업완료한 주문이 없습니다.」 (11장 F)
- 주문받기가 OFF여도 남은 주문은 그대로 보이고 처리할 수 있다 (Q04).

## 4. 로그

- 남길 것: 버튼 동작 결과는 T03이 이미 남긴다(orderId · 동작 · 결과). 이 화면은 정렬 저장 실패만 남긴다.
- 남기지 않을 것: 고객명 · 연락처 · 요청사항.

## 5. 테스트 전략

- `order-board-logic.ts`: 탭별 목록 · 취소 제외 · 오늘 결제한 픽업완료만, 최신순 / 오래된순, 필터 건수, 「+ 외 N개」, 픽업 예정 문구 4가지(가짜 시계), 12분 경고.
- 화면: 탭 전환, 정렬 저장 · 복원, 필터, 버튼별 changeStatus 호출과 요청 중 막기, 실패 토스트, 픽업완료 배너 5초 · [완료 취소], 고객 취소 배너, 빈 화면 문구, 카드가 넘칠 때만 이전/다음 버튼.
- 주문 50건을 한꺼번에 넣어도 렌더가 1초 안에 끝나는지 한 번 잰다(테스트 환경 기준, 참고 값).

## 6. 경계

- **항상**: 상태 변경은 `useOrders().changeStatus`로만. 카드에 개인정보는 서버가 가린 값만.
- **먼저 묻기**: 새 라이브러리, 이 스펙에 없는 버튼 · 문구.
- **하지 않기**: 요약 팝업 · 사유 팝업, 위젯, 출력, 알림음 반복.

## 7. 완료 기준

1. 두 탭 · 정렬 · 보기 필터가 2.1 · 2.2대로 동작하고, 첫 탭 정렬이 다시 켠 뒤에도 유지된다 (테스트).
2. 카드가 2.3 · 2.4대로 보인다: 「+ 외 N개」, 옵션 한 줄, 요청사항 2줄, 픽업 예정 4가지, 12분 경고 (테스트).
3. [주문접수] → 제조중, [제조완료] → 제조완료, [픽업완료] → 5초 배너, 5초 안 [완료 취소]면 제조완료로 돌아오고, 지나면 [픽업완료] 탭으로 간다 (테스트).
4. 실패 3종이 토스트로 보이고 카드는 그대로다 (테스트).
5. 고객 취소면 카드가 사라지고 배너 5초 + 알림음 한 번 (테스트).
6. 창 폭 1024 · 1280 · 1920에서 한 줄 3 · 4 · 6장, 카드가 넘칠 때만 이전 / 다음 버튼 (Linux 실제 창 + Windows 수동).
7. 주문 50건에서 화면이 멈추지 않는다 (테스트 + 모의 버튼으로 수동).
8. ① lint · typecheck · format · test · build · Rust 검사 통과, ② · ③ 리뷰 완료.

## 12. 개정 — 도착 예정 시각 (T19, 2026-11-25 대표님 결정, 2026-11-25 사용자 승인)

> `AGENTS.md` 확정 사항 「주문 정책 변경」 ② · ④. 이 장이 2.3 · 2.4 · 11장 B보다 우선한다. Q26의 픽업 예정 선택지(지금 · 5 · 10 · 20 · 30 · 40분 · 1시간 이상)를 바꾼다.

- 고객은 결제할 때 **도착 시각을 5분 단위로** 고른다. 가장 이른 값은 점포의 「도착 최소 시간」(환경설정, `SPEC-settings-order.md`)이다. 예: 최소 15분이면 15 · 20 · 25분 …
- 주문 데이터: 고객이 고른 값(`pickupChoice`) 대신 **도착 예정 시각**(`arrivalAt`, 서버가 결제 시각 + 고른 분으로 계산해 준다고 가정)을 받는다. 「지금」 · 「1시간 이상」 구분이 없어지므로 고른 값 자체는 필요 없다.
- 2.4 표를 이것으로 바꾼다 (예: 15:25 결제, 20분 고름):

| 경우 | 카드 표시 |
|---|---|
| 도착 전 | 「15:45 도착 (20분 뒤)」, 괄호 안이 1분마다 줄어든다 |
| 도착 시각이 지남 | 괄호 안을 빨간 글자 「3분 지남」 |

- 1분마다 시간 글자만 다시 그리는 규칙은 그대로.
- 같은 문구를 쓰는 곳: 요약 팝업 기본 정보(T05), 위젯 카드(T06), 주문내역 상세(T07), 주문서 「도착예정」 · 영수증 새 줄(T12, `SPEC-print-forms.md` 12장).
- 2.3 경고 줄의 「결제 뒤 12분」은 T20에서 「자동 취소 시간 − 3분」으로 바뀐다(`SPEC-settings-order.md`).
- 정해지지 않은 것: 고객이 고를 수 있는 가장 늦은 시각(앱 · 서버가 정함, POS는 받은 시각을 그대로 보인다).
