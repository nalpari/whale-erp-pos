# [협의 요청] 매장 주문 실시간 전달 방식

> **문서 상태**: 협의용 초안 (백엔드 PL 회의 안건)
> **작성**: 매장 주문접수 프로그램 담당
> **성격**: 방식별 특성을 중립적으로 비교한 자료입니다. 특정 방식을 권장하지 않습니다.
> **결정 필요 사항**
> 1. 결제 완료 주문을 매장 프로그램에 전달하는 방식 (아래 5가지 중 선택)
> 2. 선택한 방식의 서버 측 구현·운영 담당 (백엔드 팀 / 매장 프로그램 담당)

---

## 1. 배경

- 고객 앱에서 결제가 끝난 주문을 **매장 POS PC에 설치된 주문접수 프로그램(Tauri)** 이 받아 처리합니다.
- 매장 프로그램 → 서버 방향(접수, 거절, 제조 완료, 픽업 완료)은 **REST API**로 보냅니다. (`docs/requests/backend-api-request.md` 3.5)
- 이 문서는 반대 방향인 **서버 → 매장 프로그램으로 신규 주문을 전달하는 방식**을 다룹니다.

### 1.1 전제 조건: 연결은 매장 PC가 먼저 연다

```
✗ 서버가 매장 PC로 접속                    ✓ 매장 PC가 서버로 접속

[서버] ──X──▶ [공유기] [매장 PC]          [매장 PC] ──연결──▶ [서버]
              (공인 IP 없음, 인바운드 차단)           ◀── 이 연결/요청으로 주문 수신
```

매장 PC는 공유기(NAT) 뒤에 있어 서버가 먼저 접속할 수 없습니다. 매장마다 포트포워딩·고정 IP를 설정하는 방식은 운영·보안상 제외합니다. **아래 모든 방식은 매장 PC가 서버로 나가는 연결을 사용합니다.**

### 1.2 방식과 무관한 공통 요구사항

어떤 방식을 선택해도 아래 장치는 필요합니다. 실시간 전달은 **"빠르게"**, 아래 장치는 **"빠짐없이"** 를 담당합니다.

| 장치 | 역할 | 요청 문서 |
|---|---|---|
| 수신 확인 (ack) | 매장이 받은 주문을 서버에 확인. 미확인 주문을 서버가 감지 | 3.4 |
| 미확인 주문 조회 | 놓친 주문 수신. 재연결·재시작 시, 그리고 연결 중에도 주기적으로(예: 30~60초) 호출. 연결은 정상인데 이벤트만 빠진 경우를 잡기 위함 | 3.3 |
| 연결 감시 | 서버 하트비트가 일정 시간 오지 않으면 매장이 연결을 끊고 재연결 (①②⑤ 해당) | 3.2 |
| 중복 처리 방지 | 같은 주문이 두 번 와도 한 번만 처리 (`orderId` / `eventId`) | 3.2 |

## 2. 후보 방식

### ① WebSocket

매장이 서버와 양방향 연결을 맺고 유지합니다. 서버는 이 연결로 주문을 푸시합니다.

```
[매장 PC] ════ WebSocket 상시 연결 ════ [WebSocket 서버]
          ◀── 주문 푸시 (즉시)
```

- 표준 양방향 실시간 프로토콜. 서버 → 매장 푸시 외에 양방향 메시지도 가능
- 연결을 상시 유지하므로 서버 증설 시 메시지 라우팅 장치(Redis Pub/Sub 등) 필요 (4장 참고)
- 프록시·로드밸런서의 WebSocket 업그레이드 및 유휴 타임아웃 설정 필요

### ② SSE (Server-Sent Events)

매장이 HTTP 요청을 하나 열어 두면, 서버가 그 응답 스트림으로 이벤트를 계속 보냅니다.

```
[매장 PC] ── GET /stores/{id}/events (응답이 끝나지 않음) ──▶ [API 서버]
          ◀── event: ORDER_CREATED ... event: ORDER_CREATED ... (즉시)
```

- 일반 HTTP 기반. 별도 프로토콜 업그레이드 없음
- 서버 → 매장 단방향 (매장 → 서버는 REST로 분리되어 있어 이 구조와 맞음)
- 재연결 시 마지막 수신 이벤트 ID를 서버에 전달하는 표준 기능(`Last-Event-ID`)이 있어 놓친 이벤트 재전송에 활용 가능
- 연결을 상시 유지하므로 서버 증설 시 라우팅 장치 필요 (①과 동일)

### ③ 롱 폴링 (Long Polling)

매장이 조회 요청을 보내면, 서버는 새 주문이 생기거나 제한 시간(예: 30초)이 될 때까지 응답을 보류합니다. 매장은 응답을 받으면 즉시 다시 요청합니다.

```
[매장 PC] ── GET /orders/wait?after=… ──▶ [API 서버]  (새 주문 생길 때까지 대기, 최대 30초)
          ◀── 새 주문 응답 (즉시) 또는 빈 응답 (시간 초과)
          ── 즉시 재요청 ──▶ …
```

- 일반 REST API 형태. 서버 기술과 무관하게 구현 가능
- 요청 하나의 수명이 짧아(최대 수십 초) 배포·증설 시 영향이 작음
- 대기 중인 요청이 "다른 서버에서 생긴 주문"을 감지하려면 공유 장치(Redis 등) 또는 짧은 주기의 DB 확인 필요

### ④ 짧은 폴링 (Short Polling)

매장이 일정 간격(예: 2~3초)으로 미확인 주문 조회 API를 호출합니다.

```
[매장 PC] ── GET /orders?unacknowledged=true ──▶ [API 서버]   (3초마다 반복)
          ◀── 새 주문 목록 (없으면 빈 목록)
```

- 공통 요구사항의 "미확인 주문 조회 API"(3.3)를 그대로 사용. 추가 API 불필요
- 서버 증설 문제 없음 (상태를 들고 있는 연결이 없음)
- 전달 지연이 최대 폴링 간격만큼 발생
- 요청량 = 매장 수 ÷ 폴링 간격 (예: 100개 매장, 3초 간격 → 약 33 req/s, 1,000개 매장 → 약 333 req/s)

### ⑤ MQTT (관리형 브로커)

매장은 MQTT 브로커(AWS IoT Core, EMQX Cloud, HiveMQ Cloud 등)에 접속해 자기 매장 주제를 구독하고, 백엔드는 브로커에 발행합니다.

```
[매장 PC] ════ MQTT 연결 (구독: store/A/orders) ════ [관리형 브로커] ◀── 발행 ── [API 서버]
          ◀── 주문 전달 (즉시)
```

- 연결 관리와 라우팅을 브로커가 담당 → 백엔드는 발행만 하며 서버 증설 문제가 없음
- 전달 보장 수준(QoS) 지정 가능, 영구 세션 사용 시 매장이 오프라인인 동안의 메시지를 브로커가 보관
- 신규 인프라(브로커 서비스) 도입, 사용량 기반 비용, 매장 기기별 인증 정보(인증서 등) 관리 필요

## 4. 서버 증설 시 동작 (①②③ 해당)

상시 연결(①②) 또는 대기 요청(③)은 **특정 서버 한 대에 붙어 있습니다.** 결제 완료 처리가 다른 서버에서 일어나면 그 서버는 매장에 직접 전달할 수 없습니다.

```
[매장 A] ══▶ [서버 1]  (매장 A 연결 보유)
             [서버 2]  ◀── 결제 완료 처리 (매장 A 주문) → 매장 A 연결이 없음
```

**해결 방법**

| 방법 | 동작 |
|---|---|
| 서버 1대 운영 | 문제 없음 (파일럿 규모에서 가능) |
| Pub/Sub 방송 | 서버 2가 Redis 등에 발행 → 모든 서버가 수신 → 매장 A 연결을 가진 서버 1이 전달 |
| 연결 위치 기록 | 매장 접속 시 "매장 A → 서버 1" 기록 → 해당 서버로만 전달 |
| 연결 전담 서버 분리 | WebSocket/SSE 연결만 담당하는 서버를 별도 운영, API 서버는 발행만 |

> 라우팅 장치 없이 증설하면 일부 주문이 실시간으로 전달되지 않고 다음 미확인 주문 조회 시점에야 도착합니다(증상: "가끔 주문이 늦게 뜸"). 주기적 조회(1.2)가 있으면 지연은 조회 주기 이내로 제한되지만, 증설 전에 라우팅 장치를 준비해야 합니다.

④는 연결 상태가 없고, ⑤는 브로커가 라우팅을 담당하므로 해당하지 않습니다.

## 5. 매장 프로그램(Tauri) 측 영향

| 항목 | 내용 |
|---|---|
| 구현 위치 | 모든 방식에서 **Rust 본체**가 수신을 담당하고, 화면(Next.js)에는 Tauri 이벤트로 전달 |
| 화면 영향 | 방식과 무관하게 동일 (방식 변경 시 화면 코드 수정 없음) |

| 설정 | 수신 주소(WebSocket/SSE/브로커)와 REST API 주소를 별도 설정 가능하게 구성 |

## 6. 판단 기준: 어느 쪽이 유리한 조건인가

| 조건 | 유리한 방식 |
|---|---|
| 백엔드 추가 작업을 최소화해야 함 | ④ |
| 파일럿 일정이 촉박하고 이후 교체를 전제로 함 | ④ |
| 수 초의 지연도 허용하기 어려움 | ①②⑤ |
| 신규 인프라 도입 없이 기존 HTTP 서버로 처리하고 싶음 | ②③④ |
| 서버 → 매장 외에 양방향 실시간 메시지가 필요할 예정 | ①⑤ |
| 백엔드가 연결 관리·서버 증설 라우팅을 맡고 싶지 않음 | ④⑤ |
| 매장 수가 수백~수천 개로 빠르게 늘어날 예정 | ①②⑤ (라우팅 장치 전제) |
| 매장 오프라인 동안의 메시지를 인프라 차원에서 보관하고 싶음 | ⑤ |
| 클라우드 특정 서비스 종속을 피하고 싶음 | ①②③④ |

## 6A. 근거 자료 (공식 문서 기준)

상세 내용과 출처 링크는 `docs/research/store-order-receiver-tech-research.md` 6~7장에 있습니다.

| 사실 | 의미 | 출처 |
|---|---|---|
| 매장 PC가 먼저 나가는 연결을 열지 않으면 공유기(NAT)에 통로가 없어, 외부에서 온 연결 시도가 걸러진다 | 모든 방식에서 매장 PC가 먼저 연결해야 함 (1.1) | [RFC 5382](https://www.rfc-editor.org/rfc/rfc5382.html) |
| AWS ALB 유휴 타임아웃 기본 60초, nginx `proxy_read_timeout` 기본 60초 | ①②는 60초보다 짧은 하트비트 필요. ③은 요청 대기 시간을 60초보다 짧게 설정 | [AWS ALB](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html), [nginx](https://nginx.org/en/docs/http/websocket.html) |
| WebSocket·SSE 표준에는 메시지 단위 수신 확인(ack)·재전송이 없다 | 앱 수준 ack(REST)와 미확인 주문 조회 필요 (1.2) | [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html), [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html) |
| SSE는 재연결 시 `Last-Event-ID`를 보내고, 프록시 대비 15초 주기 주석 전송을 권장 | ②의 재전송 기준점과 하트비트 근거 | [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html) |
| 롱 폴링 타임아웃은 "generally 30 seconds is a safer value" | ③의 대기 시간 기준 | [RFC 6202](https://www.rfc-editor.org/rfc/rfc6202.html) |
| Redis Pub/Sub는 at-most-once: 끊긴 구독자에게 간 메시지는 사라진다. 더 강한 보장은 Streams | 4장 Pub/Sub 방송은 "빠른 전달"용, 누락 방지는 미확인 조회로 보완 | [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/) |
| AWS IoT Core: QoS 2 미지원, 영구 세션 기본 1시간(최대 7일), 재연결 후 저장 메시지 재과금, 세션 만료로 버려진 메시지도 과금 | ⑤도 밤새 꺼진 매장은 미확인 조회 필요 | [AWS IoT Core MQTT](https://docs.aws.amazon.com/iot/latest/developerguide/mqtt.html) |
| Idempotency-Key 헤더는 아직 IETF 초안(draft-08)이며 RFC가 아니다 | 상태 변경 API의 멱등키는 초안 기준으로 합의 필요 | [IETF Datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) |

## 7. 회의에서 결정할 것

| # | 결정 사항 | 선택지 |
|---|---|---|
| 1 | 전달 방식 | ① WebSocket / ② SSE / ③ 롱 폴링 / ④ 짧은 폴링 / ⑤ MQTT |
| 2 | 파일럿과 확장 단계의 방식 | 처음부터 최종 방식 / 파일럿은 단순 방식 후 전환 |
| 3 | 서버 측 구현 담당 | 백엔드 팀 / 매장 프로그램 담당 (①② 연결 서버를 별도로 둘 경우) |
| 4 | 서버 측 운영 담당 (배포·모니터링·장애 대응) | 백엔드 팀 / 인프라 / 매장 프로그램 담당 |
| 5 | (①②③) 서버 증설 시 라우팅 장치 | Redis Pub/Sub / 연결 위치 기록 / 연결 전담 서버 / 당분간 1대 운영 |
| 6 | (⑤) 브로커 서비스 선정과 비용 부담 | AWS IoT Core / EMQX Cloud / HiveMQ Cloud 등 |
| 7 | 결제 완료 → 전달 계층까지의 내부 흐름 | 이벤트 발행 위치와 형식 (Redis / MQ / 직접 호출) |
| 8 | 전달 지연 목표 | 예: 결제 완료 → 매장 수신 3초 이내. ④를 고르면 폴링 간격과 함께 정해야 함(3초 간격이면 3초 이내를 지키기 어려움) |
