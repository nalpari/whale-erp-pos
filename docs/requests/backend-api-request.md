# [요청] 매장 주문접수 프로그램용 백엔드 API

> **문서 상태**: 초안 (백엔드 팀 협의용)
> **요청자**: 매장 주문접수 프로그램(POS PC 설치형) 담당
> **요청 대상**: 백엔드 팀
> **목표 일정**: 2027년 2월 파일럿 매장 실사용
> **화면정의서 v0.8 반영 (2026-11-16)**: 로그인 방식, 결제정보, 매장정보·품절·인기메뉴 등 요청 범위가 늘었습니다. **7장을 먼저 봐 주세요.** 1~6장과 다른 부분은 7장이 우선합니다.
> **기획자 답변 반영 (2026-11-18)**: 화면정의서 문의 54개의 답(`docs/tasks/planner-answers.md`)에 맞춰 문서 전체를 고쳤습니다. 기획이 정한 정책(자동 취소, 매장 응답 없음, 상태 이름 등)은 "(기획 결정, Q번호)"로 표시했습니다. 백엔드에는 **할 수 있는지와 방법**만 여쭙니다.

---

## 1. 배경

- 고객 앱(앱 팀)에서 주문과 결제가 끝난 주문을 **매장 POS PC에 설치한 주문접수 프로그램**이 받아 처리합니다.
- 매장 프로그램이 하는 일: 신규 주문 알림 → 접수 또는 주문취소 → 주문서 출력 → 제조완료 → 픽업완료
- 매장 프로그램은 위 상태 변경을 백엔드에 알리고, 백엔드는 이를 고객 앱에 반영합니다(푸시, 환불 등).
- 결제, 환불, 고객 알림 발송은 **백엔드/앱 팀 담당**이고, 매장 프로그램은 "상태 변경 요청"만 보냅니다.

```
[고객 앱] ──결제 완료──▶ [백엔드] ══실시간 푸시══▶ [매장 주문접수 프로그램] ──▶ [주문서 프린터]
                           ▲                              │
                           └──────상태 변경 (REST)─────────┘
                 (주문취소 · 자동 취소 시 환불, 고객 알림은 백엔드가 처리)
```

---

## 2. 요청 API 요약

| # | API | 방향 | 용도 | 우선순위 |
|---|---|---|---|---|
| 1 | 로그인 / 인증 | 매장 → 백엔드 | 점포코드 + 매장 프로그램 비밀번호, 또는 웨일ERP 계정으로 로그인하고 토큰 발급 (7.2의 1번) | 필수 |
| 2 | **실시간 주문 푸시** | 백엔드 → 매장 | 신규 주문, 고객 취소 등을 즉시 전달 | 필수 |
| 3 | **미확인 주문 조회** | 매장 → 백엔드 | 놓친 주문 다시 받기. 재연결·재시작 시, 그리고 연결 중에도 주기적으로 호출 | 필수 |
| 4 | **수신 확인(ack)** | 매장 → 백엔드 | "이 주문 받았음" 확인. 받지 못한 주문을 백엔드가 알 수 있게 | 필수 |
| 5 | 주문 상태 변경 | 매장 → 백엔드 | 접수 / 주문취소 / 제조완료 / 픽업완료 | 필수 |
| 6 | 주문 목록·상세 조회 | 매장 → 백엔드 | 최근 한 달 주문내역, 재출력용 상세 (3.7) | 필수 |
| 7 | 테스트 주문 생성 (개발·스테이징 전용) | 개발자 → 백엔드 | 실제 결제 없이 주문을 만들어 매장 프로그램 테스트 | 필수 |

## 3. 상세 요구사항

### 3.1 로그인 / 인증

> 기기 등록 대신 **로그인 2종**을 씁니다(기획 결정, Q09). 자세한 것은 7.2의 1번과 "로그인 세부"입니다.

- **점포번호 로그인**: 점포코드(ST + 6자리) + 매장 프로그램 비밀번호. 자동 로그인을 쓸 수 있습니다. **웨일ERP 계정 로그인**: 아이디 + 비밀번호 + 점포코드. 자동 로그인 없음.
- 로그인한 PC는 **그 점포의 주문만** 받고 처리할 수 있어야 합니다. PC 한 대가 점포 하나를 맡습니다.
- 토큰 만료 시 재발급 방식(refresh token 등)이 필요합니다. 매장 PC는 며칠씩 켜져 있습니다. 웨일ERP에서 매장 프로그램 비밀번호를 바꾸면 그 점포의 재발급 토큰을 폐기해 주세요.
- **한 점포에 PC를 여러 대 쓸 수 있습니다** (기획 결정, Q13: 대수 제한 없음). 주문 상태와 주문받기는 모든 PC에 바로 반영되어야 하고, 같은 주문을 두 PC가 동시에 처리하면 먼저 도착한 것만 반영합니다(3.5의 409). 주문서 자동 출력은 [주문접수]를 누른 PC에서만 합니다.

```http
POST /store-app/login            # 주소 · 필드 이름은 예시입니다
{ "storeCode": "ST000001", "password": "...", "deviceName": "DESKTOP-AB12" }

→ 200
{ "accountType": "store", "store": { "id": "store_001", "code": "ST000001", "name": "웨일커피 본점" },
  "accessToken": "...", "refreshToken": "...", "expiresIn": 3600 }
```

### 3.2 실시간 주문 푸시

> **전달 방식은 협의 중입니다.** WebSocket 외 대안(SSE, 롱 폴링, 짧은 폴링, MQTT) 비교는 `docs/proposals/realtime-delivery-options.md` 참고. 아래 내용은 WebSocket/SSE 기준이며, 이벤트 종류·`eventId`·데이터 형식은 방식과 무관하게 적용됩니다.

- **매장 PC가 먼저 백엔드에 접속하는 방식**이어야 합니다. 매장 PC는 공유기 뒤에 있어 백엔드가 먼저 접속할 수 없습니다.
- **방식은 `docs/proposals/realtime-delivery-options.md` 협의에서 정합니다.** 이 문서는 특정 방식을 전제하지 않습니다. 매장에서 백엔드로 보내는 요청(접수, 주문취소 등)은 어느 방식에서든 REST API(3.5)로 보내므로, 양방향 통신을 위해 WebSocket을 고를 필요는 없습니다.
- (상시 연결 방식인 WebSocket·SSE를 고를 경우) 연결 유지 확인(heartbeat/ping)을 30초 이내 주기로 보내 주세요. 매장 쪽에서 끊김을 빨리 감지하기 위해서입니다.
  - 매장 프로그램은 이 신호가 일정 시간(예: 주기의 2배) 동안 오지 않으면, 연결이 살아 있어 보여도 끊고 다시 연결합니다.
- 이벤트에는 고유 `eventId`가 있어야 합니다. 같은 이벤트가 두 번 와도 매장에서 한 번만 처리할 수 있게 하기 위해서입니다.
- 이벤트는 **순서가 바뀌어 도착할 수 있습니다**(예: 취소가 생성보다 먼저 도착, 재전송된 옛 이벤트). 매장이 더 오래된 내용으로 화면을 덮어쓰지 않도록, 주문 데이터에 `updatedAt`(또는 버전 번호)을 넣어 주세요(3.6).

**이벤트 종류**

| 이벤트 | 시점 | 매장 동작 |
|---|---|---|
| `ORDER_CREATED` | 결제 완료 | 알림음 + 위젯 |
| `ORDER_CANCELED` | 고객이 접수 전 취소(고객취소), 15분 미접수 자동 취소, 다른 PC의 매장취소 | 카드 제거, 고객취소는 알림 배너 (Q19) |
| `ORDER_STATUS_CHANGED` | 다른 PC에서 접수 · 제조완료 · 픽업완료 (Q13) | 카드 · 위젯 갱신 |
| `STORE_ACCEPTING_CHANGED` | 주문받기 ON/OFF가 다른 PC에서, 또는 서버가 자동으로 바뀜 (Q13 · Q53 · Q54) | 헤더 토글 갱신. 자동 OFF면 빨간 띠 · 위젯 안내 |
| `ORDER_UPDATED` | 기타 변경 (필요 시). 결제 후 메뉴 변경을 허용하지 않으면(3.5 정책 제안) 쓰일 일이 거의 없음 | 화면 갱신 |

이벤트 이름은 제안입니다. 자동 OFF 이벤트에는 이유(매장 응답 없음 / 미접수 연속 2건)를 넣어 주세요. 화면 문구가 다릅니다.

```json
{
  "eventId": "evt_8f2a...",
  "type": "ORDER_CREATED",
  "occurredAt": "2027-02-10T08:15:30+09:00",
  "order": { "...": "3.6 주문 데이터 참고" }
}
```

### 3.3 미확인 주문 조회 (누락 방지)

실시간 연결은 인터넷이 끊긴 동안의 주문을 받을 수 없습니다. 또 연결은 정상인데 이벤트 하나만 빠지는 경우(서버 증설 시 라우팅 누락, 서버 오류 등)도 있습니다. 그래서 매장 프로그램은 아래 API를 **두 가지 시점에** 호출합니다.

| 시점 | 목적 |
|---|---|
| 재연결·프로그램 재시작 직후 | 끊겨 있던 동안의 주문 받기 |
| 연결 중에도 주기적으로 (예: 30~60초마다, 주기는 협의) | 연결은 정상인데 빠진 주문 잡기 |

- **요청**: 이 API는 매장마다 주기적으로 호출되므로, 미확인 주문이 없을 때 가볍게 응답할 수 있게 해 주세요.
- 이 주기적 호출은 "매장 프로그램이 지금 켜져 있고 접속 중"이라는 신호로도 쓸 수 있습니다(3.9 참고). 기획은 신호 간격을 15~20초로 정했습니다(Q53). 이 간격으로 조회해도 서버 부담이 괜찮은지 알려 주세요.

```http
GET /stores/{storeId}/orders?unacknowledged=true
GET /stores/{storeId}/orders?status=PAID,ACCEPTED,READY   # 처리 중인 주문 전체 (접수대기 · 제조중 · 제조완료)
```

- 백엔드는 매장이 ack하지 않은 주문을 계속 "미확인" 상태로 보관해야 합니다.

**취소·변경 알림의 누락 방지 (담당자 제안, 협의 필요)**

위 조회는 **새 주문**만 잡습니다. 매장이 이미 ack한 주문에 대해 나중에 온 취소·변경 알림이 빠지면, "미확인 주문" 조회에는 나오지 않습니다. 그러면 매장 화면에는 취소된 주문이 그대로 남습니다.

이를 막으려면 조회를 주문 단위가 아니라 **이벤트(알림) 단위**로 할 수 있어야 합니다.

```http
GET /stores/{storeId}/events?after={마지막으로 받은 eventId}
→ 200 { "events": [ { "eventId": "...", "type": "ORDER_CANCELED", ... } ], "lastEventId": "..." }
```

- 매장은 마지막으로 받은 `eventId`를 기억해 두고, 그 이후의 이벤트를 모두 받아 옵니다. 새 주문·취소·변경이 같은 방법으로 잡힙니다.
- 이 방식이면 짧은 폴링을 고를 때 이 API 하나로 실시간 수신과 누락 방지를 함께 처리할 수 있습니다.
- 이벤트 단위 조회가 어렵다면, 대안으로 "최근 N분 안에 상태가 바뀐 주문 목록" 조회도 가능합니다. 어느 쪽이 백엔드 구조에 맞는지 알려 주세요.
- 취소 알림이 늦더라도 잘못 제조하는 일은 3.5의 정책(접수 성공 후에만 제조 시작)으로 막습니다. 이 조회는 화면을 실제 상태와 맞추기 위한 것입니다.

### 3.4 수신 확인 (ack)

```http
POST /orders/{orderId}/ack
{ "deviceId": "dev_123" }
```

- 매장이 주문을 받아 화면에 표시한 뒤 호출합니다.
- **요청**: ack가 일정 시간(예: 1분) 안에 오지 않는 주문은 백엔드에서 감지할 수 있게 해 주세요(로그·알림 등). 매장 프로그램이 꺼져 있거나 연결이 끊긴 상황을 잡아내기 위해서입니다.

### 3.5 주문 상태 변경

**상태 흐름 (기획 결정, Q16 · Q17 · Q19 · Q20. 코드 이름은 제안이며 백엔드 기준에 맞춥니다)**

화면 이름은 매장 · 고객 앱 모두 **접수대기 → 제조중 → 제조완료 → 픽업완료**입니다. [주문접수]를 누르는 순간이 제조 시작이고, 따로 "제조시작" 단계는 없습니다(Q16).

```
PAID(접수대기) ──[주문접수]──▶ ACCEPTED(제조중) ──[제조완료]──▶ READY(제조완료) ──[픽업완료]──▶ PICKED_UP(픽업완료)
  │                              │
  │                              └──[주문취소]──▶ STORE_CANCELED(매장취소)
  ├──[주문취소]──▶ STORE_CANCELED(매장취소)      (백엔드: 자동 환불 + 고객 안내)
  ├──고객 취소──▶ CUSTOMER_CANCELED(고객취소)    (접수대기에서만, 백엔드 → 매장으로 푸시)
  └──15분 미접수──▶ 자동 취소(매장취소로 기록)    (서버가 처리, 매장 프로그램이 꺼져 있어도)
```

| 요청 | API | 필수 값 | 백엔드 후속 처리 (백엔드/앱 팀) |
|---|---|---|---|
| 접수 | `POST /orders/{id}/accept` | — (예상 시간 입력 없음) | 고객에게 "[접수완료] 상품이 제조중입니다" 알림 |
| 주문취소 | `POST /orders/{id}/cancel` | 취소 사유 (아래) | **결제 취소/환불**(쿠폰 · 스탬프 · 포인트 복원), 고객에게 사유 안내 |
| 제조완료 | `POST /orders/{id}/ready` | — | 고객에게 "[제조완료] 픽업대에서 수령하세요" 알림 |
| 픽업완료 | `POST /orders/{id}/complete` | — | 주문 종료. **고객 알림 없음**, 앱은 단계 바만 바뀜 (Q22) |

- 주문취소는 접수대기 · 제조중에서만 됩니다. 제조완료 · 픽업완료 뒤에는 매장 프로그램에서 취소할 수 없고 고객센터로 처리합니다 (Q17).
- 픽업완료를 누르면 매장 화면에 5초 동안 "완료 취소"가 보입니다(Q22). 매장 프로그램은 **5초가 지난 뒤에** 픽업완료를 보내므로 되돌리기 API는 필요 없습니다.
- 0시에 제조중 · 제조완료로 남은 주문은 자동으로 픽업완료 처리합니다(기획 결정, Q21). 매장 프로그램이 꺼져 있어도 되도록 서버에서 해 주세요. 고객 알림은 보내지 않습니다.
- 미접수 15분 자동 취소 때 고객 문구: "매장이 주문을 확인하지 못했습니다. 결제 금액은 자동 환불됩니다." (Q20)

```http
POST /orders/{orderId}/accept
Idempotency-Key: 7c1e...           # 같은 요청 재전송 시 중복 처리 방지

→ 200 { "orderId": "...", "status": "ACCEPTED", "updatedAt": "..." }
→ 409 { "code": "INVALID_TRANSITION", "currentStatus": "CANCELED" }   # 이미 고객이 취소한 경우 등
```

- **멱등키(Idempotency-Key) 지원**: 네트워크가 불안정하면 매장에서 같은 요청을 다시 보낼 수 있습니다. 같은 키의 요청은 한 번만 처리해 주세요.
- **잘못된 상태 전환은 409로 거절**하고 현재 상태를 돌려주세요. 예: 고객 취소와 매장 접수가 동시에 일어난 경우.
- **취소 사유 (기획 결정, Q18)**: 고객에게 그대로 보이는 문장입니다. ① 재료가 소진되었습니다 ② 주문이 많아 준비가 어렵습니다 ③ 영업이 종료되었습니다 ④ 매장 사정으로 주문을 취소합니다 ⑤ 직접 입력(50자, 줄바꿈 없음). 코드로 보낼지 문장으로 보낼지는 협의합니다. 고객 문구는 "매장 사정으로 주문이 취소되었습니다. 결제 금액은 자동 환불됩니다." + 사유 줄입니다 (Q17).

**취소·변경 정책 제안 (담당자 제안, 협의 필요)**

매장 화면은 실제 상태보다 몇 초 늦을 수 있습니다(특히 짧은 폴링). 그 사이에 고객이 취소하면 매장이 취소된 주문을 만들 위험이 있습니다. 아래 규칙이면 화면이 늦어도 잘못 제조하지 않습니다.

| # | 제안 | 이유 |
|---|---|---|
| 1 | **고객 취소는 매장 접수 전까지만 가능** (기획 결정, Q19). 접수 후에는 고객이 앱에서 취소·변경할 수 없음 | 제조가 시작된 뒤의 취소를 막음 |
| 2 | **고객 취소와 매장 접수가 겹치면 백엔드가 먼저 도착한 쪽을 인정**하고, 늦은 쪽은 409로 거절 (기획 결정, Q19 · Q13). 매장 문구 "고객이 이미 취소한 주문입니다." / "다른 PC에서 이미 처리한 주문입니다.", 고객 문구 "주문을 취소할 수 없습니다. 매장에 문의해 주세요." | 판정을 한곳(백엔드)에서 해야 매장 화면이 늦어도 결과가 틀리지 않음. 위 409 응답이 이 용도 |
| 3 | **매장 프로그램은 접수 성공 응답(200)을 받은 뒤에만 주문서를 출력**하고 제조 시작을 안내 | 접수가 409로 거절되면(이미 취소됨) 주문서가 나오지 않음 |
| 4 | **결제 후 메뉴 변경은 허용하지 않음.** 바꾸려면 취소 후 다시 주문 | 금액이 달라져 추가 결제·부분 환불이 생기고, 제조 중 변경은 매장에서 받기 어려움 |
| 5 | 접수 후 취소가 필요하면 **매장이 [주문취소]** (제조중까지, 기획 결정 Q17) | 제조완료 뒤는 고객센터 |


### 3.6 주문 데이터 (주문서 출력에 필요한 항목)

```json
{
  "orderId": "2702100000010001",
  "displayNumber": "108",
  "storeId": "store_001",
  "status": "PAID",
  "orderType": "TAKEOUT",
  "paidAt": "2027-02-10T08:15:30+09:00",
  "updatedAt": "2027-02-10T08:15:30+09:00",
  "items": [
    {
      "itemId": "oi_1",
      "menuName": "카페라떼",
      "quantity": 2,
      "unitPrice": 4500,
      "options": [
        { "groupName": "온도", "optionName": "ICE", "quantity": 1, "price": 0 },
        { "groupName": "우유", "optionName": "오트밀크", "quantity": 1, "price": 800 },
        { "groupName": "샷", "optionName": "샷 추가", "quantity": 2, "price": 1000 }
      ],
      "lineTotal": 12600
    }
  ],
  "customerRequest": "얼음 조금만 주세요",
  "pickupChoice": "20min",
  "payment": { "totalAmount": 12600, "discountAmount": 0, "paidAmount": 12600 },
  "customer": { "maskedName": "박*준", "phoneLast4": "1234", "orderCount": 3 }
}
```

| 항목 | 필요 이유 |
|---|---|
| `orderId` | 주문번호. **YYMMDD + 점포코드 숫자 6자리 + 일련번호 4자리 = 16자리** (기획 결정, Q28. 앱 정의서의 19자리에서 바뀜). 화면 · 검색 · 영수증에 씀 |
| `displayNumber` | 픽업번호. **점포별로 매일 0시에 1번부터**, 앞자리 0 없이 #1~#9999, 넘으면 다시 1, 취소된 번호는 다시 쓰지 않음 (기획 결정, Q25) |
| `pickupChoice` | 고객이 고른 픽업 시각(지금 · 5 · 10 · 20 · 30 · 40분 · 1시간 이상). 매장은 결제 시각 + 이 값으로 예정 시각을 계산 (Q26) |
| `options[].groupName / optionName` | 주문서에 그대로 출력. **표시용 이름을 백엔드에서 내려 주세요** (매장에서 코드→이름 변환 안 함) |
| `options[].quantity` | 샷 추가, 시럽 펌프 수 등 수량형 옵션 |
| `updatedAt` (또는 버전 번호) | 주문이 마지막으로 바뀐 시각. 매장은 가지고 있는 것보다 오래된 내용이 오면 무시함 (이벤트 순서 뒤바뀜 대비) |
| `orderType` | 매장 / 포장 구분 (컵 종류 결정) |
| `customerRequest` | 고객 요청사항 출력 |
| `customer` | 픽업 시 본인 확인용. **개인정보 최소화**: 이름은 가린 값(박*준)만, 전화번호는 끝 4자리만(주문내역 검색에도 씀, Q36). `orderCount`는 이 고객이 이 점포에서 결제한 누적 주문 수(이번 주문 포함, 취소 제외, 기간 제한 없음, Q29) |

### 3.7 주문 목록·상세 조회

```http
GET /stores/{storeId}/orders?from=2027-01-10&to=2027-02-10&status=...&q=...&page=1&size=50
GET /orders/{orderId}
```

- 주문내역 화면, 주문서 재출력, 프로그램 재시작 후 화면 복구에 사용합니다.
- **조회 범위는 최근 한 달**(한 달 전 같은 날 ~ 오늘, 하루 기준 0시)입니다. 그 전은 웨일ERP에서 봅니다 (기획 결정, Q34).
- 검색은 휴대폰 번호 끝 4자리 · 픽업번호 · 주문번호로 하고, 선택한 기간과 상관없이 최근 한 달 전체에서 찾습니다. 고객명 검색은 하지 않습니다 (Q36).
- 상태별 건수와 결제 합계(할인 뒤 결제금액, 취소 건 제외)가 필요합니다. 상태 탭은 전체 · 접수대기 · 제조중 · 제조완료 · 픽업완료 · 취소(매장취소 + 고객취소)입니다 (Q17 · Q19 · Q35).
- 페이지당 20 / 50 / 100건 (Q37).

### 3.8 테스트 주문 생성 (개발·스테이징 전용)

```http
POST /dev/stores/{storeId}/test-orders
{ "items": [ ... ] }    # 생략 시 임의 주문 생성
```

- 실제 결제 없이 주문을 만들어 매장 프로그램을 개발·테스트합니다.
- **피크타임 재현용으로 짧은 시간에 여러 건 생성**할 수 있으면 좋습니다(예: 1분에 30건).
- 운영 환경에서는 비활성화합니다.

### 3.9 매장 프로그램이 꺼져 있을 때의 주문 (기획 결정, Q20 · Q53 · Q54)

**문제**: 매장 PC가 꺼져 있거나 인터넷이 끊겨 있어도 고객은 앱에서 결제할 수 있습니다. 그러면 결제는 끝났는데 매장은 주문이 온 줄 모릅니다. 매장이 다시 접속하면 밀린 주문이 한꺼번에 나타나지만 이미 늦습니다.

```
[고객 앱] ──결제 완료──▶ [백엔드] ──X──▶ [매장 프로그램: 꺼짐 / 인터넷 끊김]
   고객은 주문이 접수된 줄 알고 매장으로 출발            매장은 모름
```

기획이 아래처럼 정했습니다. 백엔드에는 서버에서 할 수 있는지와 부담만 여쭙니다. 시간 · 건수는 운영하며 조정할 값입니다.

| 상황 | 기획 결정 | 서버가 할 일 |
|---|---|---|
| 매장 응답 없음 (PC 꺼짐 · 강제 종료 · 인터넷 끊김) (Q53) | 매장 프로그램이 15~20초마다 연결 신호를 보내고, **1분 동안 신호가 없으면 그 점포 주문받기를 OFF**. 고객 앱에는 "준비중" | 신호 확인, 자동 OFF. 매장이 다시 연결되면 인터넷만 잠깐 끊긴 경우 직전 상태로 돌아감(Q51). PC를 다시 켠 경우는 매장 프로그램이 OFF로 시작(Q03) |
| 1분 사이에 들어오는 주문 (Q53) | 고객이 [결제하기]를 누를 때 매장의 마지막 신호가 **30초 넘었으면 결제하지 않고** "매장이 지금 주문을 받을 수 없습니다." | 결제 전 확인 (앱 팀과 함께) |
| 이미 결제된 주문 (Q53) | 서버가 보관했다가 매장이 다시 연결되면 접수대기로 보냄 | 3.3 조회로 다시 받음 |
| 미접수 주문 (Q20) | 접수대기 **15분**이면 자동 취소 + 자동 환불. 매장 프로그램이 꺼져 있어도 | 서버 타이머. 매장에는 취소 이벤트 |
| 미접수 자동 취소 반복 (Q54) | 미접수 자동 취소가 **연속 2건**이면 주문받기 OFF. 사이에 접수한 주문이 있으면 0부터. 매장취소 · 고객취소는 세지 않음. 자동으로 다시 켜지 않음 | 횟수 세기, 자동 OFF, 매장에 이유와 함께 이벤트 (3.2) |
| 영업 시간 외 주문 | 기획 답변 없음. 매장 프로그램은 켤 때마다 주문받기 OFF로 시작하고 점원이 직접 켭니다(Q03) | 5장 질문 8 |

- **매장 프로그램이 제공하는 것**: 15~20초 간격의 연결 신호. 3.3의 주기적 조회를 그대로 신호로 써도 되고, 별도 신호가 필요하면 맞추겠습니다.
- 주문 차단과 환불, 고객 알림은 백엔드/앱 팀 영역이며, 매장 프로그램은 그 결과(취소 · 주문받기 변경 이벤트)를 화면에 반영합니다.

## 5. 백엔드 팀에 묻고 싶은 것

> 2026-11-18 기획자 답변으로 정책이 정해진 질문은 **(기획 결정)**으로 표시했습니다. 그 질문은 서버에서 할 수 있는지만 답해 주세요. **아직 열린 것: 4, 6, 8, 10(일부), 11, 12번.**

1. **미접수 주문 자동 처리 (기획 결정, Q20 · Q54)**: 15분 미접수면 서버가 자동 취소 · 환불, 연속 2건이면 주문받기 자동 OFF(3.9). 서버 타이머로 할 수 있는지, 매장에 어떤 이벤트로 알릴지 알려 주세요.
2. **고객 취소 허용 범위 (기획 결정, Q19)**: 접수대기에서만 가능, 겹치면 먼저 도착한 쪽을 인정(3.5 정책 1 · 2).
3. **매장 일시 중지 (기획 결정)**: 헤더의 주문받기 ON/OFF가 이 기능입니다(7.2의 2번). OFF면 고객 앱에 "준비중".
4. **실시간 방식**: 이미 운영 중인 실시간 서버(예: 고객 앱에 주문 상태를 보내는 WebSocket/SSE 서버)가 있나요? 있다면 같이 쓰는 것이 유리하고, 없다면 파일럿은 짧은 폴링으로 시작하는 방안도 있습니다. 방식 비교와 결정은 `docs/proposals/realtime-delivery-options.md`에서 다룹니다.
5. **주문번호 규칙 (기획 결정, Q25 · Q28)**: 픽업번호는 점포별 매일 0시에 1번부터, 주문번호는 16자리(3.6).
6. **품절 처리**: 메뉴품절은 범위에 들어갔습니다(7.2의 6번). 웨일ERP와 같은 데이터입니다(기획 결정, Q41). API를 누가 언제 만드나요?
7. **매장 미접속 시 주문 차단 (기획 결정, Q53)**: 1분 무응답이면 자동 OFF, 결제 전 30초 확인(3.9). 15~20초 신호 간격이 서버에 부담이 없는지 알려 주세요.
8. **영업 시간 외 주문**: 영업 시간이 아닐 때 주문을 막는 것은 어디에서 담당하나요? 영업 시간은 누가 어디에 설정하나요? (기획 답변 없음. 매장 프로그램은 켤 때마다 주문받기 OFF로 시작, Q03)
9. **접수 후 매장 취소 (기획 결정, Q17 · Q21)**: 제조중까지 [주문취소] 가능, 환불은 접수 전과 같음(3.5). 고객이 찾아가지 않은 주문은 0시 자동 픽업완료, 환불이 필요하면 고객센터.
10. **PC 여러 대 (기획 결정, Q13)**: 대수 제한 없음, 주문서는 [주문접수]를 누른 PC에서만 출력(3.1). 남은 질문: ack는 한 대만 보내도 되는지, 모든 PC에 상태 변경을 어떻게 보낼지.
11. **결제 후 메뉴 변경**: 고객이 결제한 뒤 메뉴나 옵션을 바꿀 수 있게 하나요? 담당자 제안은 "허용하지 않음, 취소 후 다시 주문"입니다(3.5 정책 제안 4). 허용한다면 추가 결제·부분 환불과 매장 알림(`ORDER_UPDATED`) 방식을 정해야 합니다. 기획자 답변에는 결제 후 변경 기능이 없습니다.
12. **이벤트 단위 조회**: 3.3의 `GET /stores/{storeId}/events?after=...` 같은 조회를 제공할 수 있나요? 취소·변경 알림이 빠졌을 때 잡기 위한 것입니다.

#### 로그인 세부 (기획자 답변 Q09 · Q11 · Q13, 2026-11-18)

매장 프로그램은 아래를 가정하고 모의 서버로 만들었습니다. 실제와 다르면 알려 주세요.

| 항목 | 매장 프로그램이 기대하는 것 | 왜 필요한가 |
|---|---|---|
| 오류 구분 | 틀림 · 픽업오더 미구독 점포 · 관리할 수 없는 점포(웨일ERP 계정) · 매장 프로그램 비밀번호 미설정 · 잠김 · 재발급 토큰 만료를 서로 다른 오류로 | 화면에 다른 안내 문구를 보입니다. 틀림은 아이디와 비밀번호 중 어느 쪽인지 구분하지 않습니다 |
| 로그인 잠금 | 연속 5번 틀리면 그 PC만 5분 잠금. **서버가 판단**하고 매장 프로그램은 "잠김" 응답에 문구만 보입니다. 비밀번호를 바꾸면 잠금도 풀립니다 | "그 PC만" 잠그려면 서버가 PC를 구분해야 합니다 |
| PC 이름 | 로그인 요청에 Windows 컴퓨터 이름을 보냅니다(없으면 빈 값) | PC별 잠금, 새 PC 첫 로그인 알림(Q11)에 씁니다 |
| 새 PC 로그인 알림 | 그 점포에 처음 로그인한 PC일 때 웨일ERP 운영 알림으로 관리 계정에 알림 (Q11) | 매장 프로그램은 보내지 않습니다 (서버 · 웨일ERP 담당) |
| 비밀번호 변경 | 웨일ERP 점포 상세에서 매장 프로그램 비밀번호를 바꾸면 그 점포의 재발급 토큰을 폐기 | 자동 로그인된 PC가 다음 실행 때 새 비밀번호로 다시 로그인하게 합니다 (퇴사자 · 유출 대비) |
| 매장 프로그램 비밀번호 설정 | 웨일ERP 점포 상세에 설정 기능 (픽업오더 구독 점포만) | 웨일ERP 추가 개발 (Q09). 이 규칙(제안: 영문 · 숫자 6~20자)은 웨일ERP 비밀번호 규칙(3종 8자 · 2종 10자 이상)보다 약해 기획자에게 확인할 예정입니다 |

### 7.3 추가로 묻고 싶은 것

13. **매장 프로그램이 갑자기 꺼졌을 때의 주문받기 상태 (기획 결정, Q53)**: 1분 동안 신호가 없으면 서버가 주문받기를 OFF로 바꿉니다(3.9). 할 수 있는지 알려 주세요.
14. **결제 정보 전달 범위**: 영수증 출력을 위해 카드 승인 정보를 매장 프로그램이 받아야 합니다. 가린 값만 받으면 되는데, 전달해도 되는 범위를 알려 주세요.
15. **계정 권한 판정**: 점포번호 계정은 AI챗봇 인기메뉴 설정을 바꿀 수 없습니다(위젯 · 프린터 설정은 PC에 저장하므로 서버와 무관, 기획자 Q10). 서버에 저장하는 설정(인기메뉴)은 백엔드에서도 권한을 확인해야 합니다.
16. **웨일ERP 계정과 점포** (해결, 기획자 Q09): 로그인할 때 점포코드를 함께 보내므로 응답은 그 점포 하나입니다. 그 계정이 관리하지 않는 점포면 오류로 답해 주세요.
17. **품절과 ERP (기획 결정, Q41)**: 같은 데이터입니다. 웨일ERP와 매장 프로그램 어느 쪽에서 바꿔도 같이 바뀌어야 합니다.
18. **점포의 주문받기 상태 조회 API** (2026-11-16 추가): 매장 프로그램이 비정상으로 꺼지면(작업 관리자로 강제 종료, 정전 등) "주문 중단"을 보내지 못해 서버에는 "주문 받음"으로 남을 수 있습니다. 매장 프로그램은 다시 켜면 "주문 중단" 상태로 시작하므로 화면과 서버가 어긋납니다. 로그인 직후 서버의 현재 상태를 조회할 수 있게 해 주세요. 13번(신호가 끊긴 점포 처리)과 함께 정하면 좋습니다.
19. **자동 로그인용 재발급 토큰의 최대 길이** (2026-11-16 추가): 매장 프로그램은 자동 로그인을 위해 재발급 토큰을 Windows 자격 증명 관리자에 저장합니다. 자격 증명 관리자는 한 항목에 저장할 수 있는 크기에 한도가 있어(약 2.5KB로 알려져 있으나 공식 문서로는 확인하지 못함), 토큰이 이보다 길면 저장이 실패합니다. 재발급 토큰의 최대 길이를 알려 주세요.
