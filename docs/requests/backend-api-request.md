# [요청] 매장 주문접수 프로그램용 백엔드 API

> **문서 상태**: 초안 (백엔드 팀 협의용)
> **요청자**: 매장 주문접수 프로그램(POS PC 설치형) 담당
> **요청 대상**: 백엔드 팀
> **목표 일정**: 2027년 2월 파일럿 매장 실사용

---

## 1. 배경

- 고객 앱(앱 팀)에서 주문과 결제가 끝난 주문을 **매장 POS PC에 설치한 주문접수 프로그램**이 받아 처리합니다.
- 매장 프로그램이 하는 일: 신규 주문 알림 → 접수/거절 → 주문서 출력 → 제조 완료 → 픽업 완료
- 매장 프로그램은 위 상태 변경을 백엔드에 알리고, 백엔드는 이를 고객 앱에 반영합니다(푸시, 환불 등).
- 결제, 환불, 고객 알림 발송은 **백엔드/앱 팀 담당**이고, 매장 프로그램은 "상태 변경 요청"만 보냅니다.

```
[고객 앱] ──결제 완료──▶ [백엔드] ══실시간 푸시══▶ [매장 주문접수 프로그램] ──▶ [주문서 프린터]
                           ▲                              │
                           └──────상태 변경 (REST)─────────┘
                    (거절 시 환불, 완료 시 고객 알림은 백엔드가 처리)
```

---

## 2. 요청 API 요약

| # | API | 방향 | 용도 | 우선순위 |
|---|---|---|---|---|
| 1 | 기기 등록 / 인증 | 매장 → 백엔드 | 설치한 PC를 특정 매장에 연결, 인증 토큰 발급 | 필수 |
| 2 | **실시간 주문 푸시** | 백엔드 → 매장 | 신규 주문, 고객 취소 등을 즉시 전달 | 필수 |
| 3 | **미확인 주문 조회** | 매장 → 백엔드 | 재연결·재시작 시 놓친 주문 다시 받기 | 필수 |
| 4 | **수신 확인(ack)** | 매장 → 백엔드 | "이 주문 받았음" 확인. 받지 못한 주문을 백엔드가 알 수 있게 | 필수 |
| 5 | 주문 상태 변경 | 매장 → 백엔드 | 접수 / 거절 / 제조 완료 / 픽업 완료 | 필수 |
| 6 | 주문 목록·상세 조회 | 매장 → 백엔드 | 오늘 주문 내역, 재출력용 상세 | 필수 |
| 7 | 테스트 주문 생성 (개발·스테이징 전용) | 개발자 → 백엔드 | 실제 결제 없이 주문을 만들어 매장 프로그램 테스트 | 필수 |

## 3. 상세 요구사항

### 3.1 기기 등록 / 인증

- 매장 PC에 프로그램을 설치하면 **매장 코드(또는 점주 로그인)** 로 기기를 등록합니다.
- 등록된 기기는 **자기 매장의 주문만** 받고 처리할 수 있어야 합니다.
- 기기별 토큰을 발급하고, 본사/관리자가 기기 등록을 해제(토큰 폐기)할 수 있어야 합니다.
- 토큰 만료 시 재발급 방식(refresh token 등)이 필요합니다. 매장 PC는 며칠씩 켜져 있습니다.

```http
POST /store-devices/register
{ "storeCode": "WH-0001", "deviceName": "카운터 POS", "registrationCode": "..." }

→ 200
{ "deviceId": "dev_123", "storeId": "store_001", "storeName": "웨일커피 본점",
  "accessToken": "...", "refreshToken": "...", "expiresIn": 3600 }
```

### 3.2 실시간 주문 푸시

> **전달 방식은 협의 중입니다.** WebSocket 외 대안(SSE, 롱 폴링, 짧은 폴링, MQTT) 비교는 `docs/proposals/realtime-delivery-options.md` 참고. 아래 내용은 WebSocket/SSE 기준이며, 이벤트 종류·`eventId`·데이터 형식은 방식과 무관하게 적용됩니다.

- **매장 PC가 백엔드에 연결을 열고 유지하는 방식**이어야 합니다. 매장 PC는 공유기 뒤에 있어 백엔드가 먼저 접속할 수 없습니다.
- 방식은 **WebSocket 선호**, SSE도 가능합니다. 백엔드 팀 인프라에 맞게 결정하면 됩니다.
- 연결 유지 확인(heartbeat/ping)을 30초 이내 주기로 보내 주세요. 매장 쪽에서 끊김을 빨리 감지하기 위해서입니다.
- 이벤트에는 고유 `eventId`가 있어야 합니다. 같은 이벤트가 두 번 와도 매장에서 한 번만 처리할 수 있게 하기 위해서입니다.

**이벤트 종류**

| 이벤트 | 시점 | 매장 동작 |
|---|---|---|
| `ORDER_CREATED` | 결제 완료 | 알림음 + 팝업 |
| `ORDER_CANCELED` | 고객이 접수 전 취소 | 목록에서 제거, 알림 |
| `ORDER_UPDATED` | 기타 변경 (필요 시) | 화면 갱신 |

```json
{
  "eventId": "evt_8f2a...",
  "type": "ORDER_CREATED",
  "occurredAt": "2027-02-10T08:15:30+09:00",
  "order": { "...": "3.6 주문 데이터 참고" }
}
```

### 3.3 미확인 주문 조회 (누락 방지)

실시간 연결은 인터넷이 끊긴 동안의 주문을 받을 수 없습니다. **재연결·프로그램 재시작 시 아래 API로 놓친 주문을 받아옵니다.**

```http
GET /stores/{storeId}/orders?unacknowledged=true
GET /stores/{storeId}/orders?status=PAID,ACCEPTED,READY   # 처리 중인 주문 전체
```

- 백엔드는 매장이 ack하지 않은 주문을 계속 "미확인" 상태로 보관해야 합니다.

### 3.4 수신 확인 (ack)

```http
POST /orders/{orderId}/ack
{ "deviceId": "dev_123" }
```

- 매장이 주문을 받아 화면에 표시한 뒤 호출합니다.
- **요청**: ack가 일정 시간(예: 1분) 안에 오지 않는 주문은 백엔드에서 감지할 수 있게 해 주세요(로그·알림 등). 매장 프로그램이 꺼져 있거나 연결이 끊긴 상황을 잡아내기 위해서입니다.

### 3.5 주문 상태 변경

**상태 흐름 (명칭은 제안이며 백엔드 기준에 맞춥니다)**

```
PAID ──접수──▶ ACCEPTED ──제조 완료──▶ READY ──픽업 완료──▶ PICKED_UP
  │
  ├──거절──▶ REJECTED     (백엔드: 자동 환불 + 고객 안내)
  └──고객 취소──▶ CANCELED (접수 전만 가능, 백엔드 → 매장으로 푸시)
```

| 요청 | API | 필수 값 | 백엔드 후속 처리 (백엔드/앱 팀) |
|---|---|---|---|
| 접수 | `POST /orders/{id}/accept` | 예상 소요시간(분) | 고객에게 접수·예상시간 알림 |
| 거절 | `POST /orders/{id}/reject` | 거절 사유 코드 | **결제 취소/환불**, 고객에게 사유 안내 |
| 제조 완료 | `POST /orders/{id}/ready` | — | 고객에게 "준비 완료" 알림 |
| 픽업 완료 | `POST /orders/{id}/complete` | — | 주문 종료 |

```http
POST /orders/{orderId}/accept
Idempotency-Key: 7c1e...           # 같은 요청 재전송 시 중복 처리 방지
{ "estimatedMinutes": 10 }

→ 200 { "orderId": "...", "status": "ACCEPTED", "updatedAt": "..." }
→ 409 { "code": "INVALID_TRANSITION", "currentStatus": "CANCELED" }   # 이미 고객이 취소한 경우 등
```

- **멱등키(Idempotency-Key) 지원**: 네트워크가 불안정하면 매장에서 같은 요청을 다시 보낼 수 있습니다. 같은 키의 요청은 한 번만 처리해 주세요.
- **잘못된 상태 전환은 409로 거절**하고 현재 상태를 돌려주세요. 예: 고객 취소와 매장 접수가 동시에 일어난 경우.
- **거절 사유 코드(제안)**: `SOLD_OUT`(재료 소진), `TOO_BUSY`(주문 폭주), `STORE_CLOSING`(영업 종료), `ETC`(기타, 메모 포함)

### 3.6 주문 데이터 (주문서 출력에 필요한 항목)

```json
{
  "orderId": "ord_20270210_0001",
  "displayNumber": "108",
  "storeId": "store_001",
  "status": "PAID",
  "orderType": "TAKEOUT",
  "paidAt": "2027-02-10T08:15:30+09:00",
  "items": [
    {
      "itemId": "oi_1",
      "menuName": "카페라떼",
      "quantity": 2,
      "unitPrice": 4500,
      "options": [
        { "groupName": "온도", "optionName": "ICE", "quantity": 1, "price": 0 },
        { "groupName": "우유", "optionName": "오트밀크", "quantity": 1, "price": 800 },
        { "groupName": "샷", "optionName": "샷 추가", "quantity": 2, "price": 1000 }
      ],
      "lineTotal": 12600
    }
  ],
  "customerRequest": "얼음 조금만 주세요",
  "payment": { "totalAmount": 12600, "discountAmount": 0, "paidAmount": 12600 },
  "customer": { "nickname": "웨일", "phoneLast4": "1234" }
}
```

| 항목 | 필요 이유 |
|---|---|
| `displayNumber` | 주문서·호출에 쓰는 짧은 번호. **매장별·일자별 번호 규칙** 협의 필요 |
| `options[].groupName / optionName` | 주문서에 그대로 출력. **표시용 이름을 백엔드에서 내려 주세요** (매장에서 코드→이름 변환 안 함) |
| `options[].quantity` | 샷 추가, 시럽 펌프 수 등 수량형 옵션 |
| `orderType` | 매장 / 포장 구분 (컵 종류 결정) |
| `customerRequest` | 고객 요청사항 출력 |
| `customer` | 픽업 시 본인 확인용. **개인정보 최소화**: 전체 전화번호 불필요 |

### 3.7 주문 목록·상세 조회

```http
GET /stores/{storeId}/orders?date=2027-02-10&status=...
GET /orders/{orderId}
```

- 오늘 주문 내역 화면, 주문서 재출력, 프로그램 재시작 후 화면 복구에 사용합니다.

### 3.8 테스트 주문 생성 (개발·스테이징 전용)

```http
POST /dev/stores/{storeId}/test-orders
{ "items": [ ... ] }    # 생략 시 임의 주문 생성
```

- 실제 결제 없이 주문을 만들어 매장 프로그램을 개발·테스트합니다.
- **피크타임 재현용으로 짧은 시간에 여러 건 생성**할 수 있으면 좋습니다(예: 1분에 30건).
- 운영 환경에서는 비활성화합니다.

## 4. 비기능 요구사항

| 항목 | 요청 |
|---|---|
| 전달 지연 | 결제 완료 → 매장 수신 **3초 이내** (목표, 협의 가능) |
| 전달 보장 | **최소 1회 전달** + 미확인 주문 조회로 누락 0건. 중복은 매장이 `eventId`/`orderId`로 걸러냄 |
| 환경 | **스테이징 환경** 제공 (2026년 12월 중 희망) |
| 문서 | OpenAPI(Swagger) 스펙, 에러 코드 목록 |
| 에러 형식 | 공통 형식 `{ "code": "...", "message": "..." }` |
| 시간 | ISO 8601, 한국 시간대(+09:00) 포함 |
| 버전 | API 경로 또는 헤더로 버전 관리 (예: `/v1/...`). 매장에 설치된 구버전 프로그램이 한동안 남아 있기 때문 |

## 5. 백엔드 팀에 묻고 싶은 것

1. **미접수 주문 자동 처리**: 매장이 N분 동안 접수하지 않으면 자동으로 거절·환불하나요? 그렇다면 N은 몇 분이고, 매장에는 어떻게 알려 주나요?
2. **고객 취소 허용 범위**: 접수 전에만 가능한가요? 접수 후 취소는 매장 승인이 필요한가요?
3. **매장 일시 중지**: 피크타임에 매장이 "주문 잠시 받지 않음"을 켜는 기능이 필요할 수 있습니다. 백엔드/앱에서 지원 계획이 있나요? (파일럿 범위 밖이면 이후 단계로 미룹니다)
4. **실시간 방식**: WebSocket과 SSE 중 백엔드 인프라에 맞는 쪽은 무엇인가요?
5. **주문번호 규칙**: `displayNumber`는 매일 1번부터 다시 시작하나요?
6. **품절 처리**: 매장에서 메뉴 품절을 설정하는 기능이 필요할 경우 API를 누가 언제 만드나요? (파일럿 범위 협의 필요)
